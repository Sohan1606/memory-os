# MEMORY//OS V10.1 — Runtime Integration Architecture

## Status

Implemented on `feature/v10.1-runtime-integration`. Not merged, not tagged,
not released.

## 1. What V10.1 actually is

V10.0.1 shipped seven working Cognitive Self-Maintenance services
(`CognitiveDebtService`, `ContradictionEngine`, `UnknownService`,
`ModelErrorService`, `MaintenanceProposalService`, `CognitiveHealthService`,
`SelfMaintenanceOrchestrator`) reachable only through explicit
`/api/v10/*` endpoints.

V10.1 connects those services to the normal conversational turn. It adds
exactly one new backend module and small, surgical extensions to existing
files. There is no new table, no new endpoint, no second event store, no
second personal-state authority, and no background scheduler.

## 2. Runtime integration point

The integration lives at the tail of `Cognition.process_turn()`
(`backend/app/cognition/orchestrator.py`), after the established V9 work
(meaning → world → retrieval → arbitration → context → predictions →
attention) and before the trace is returned:

```
process_turn()
  ... existing V9 pipeline ...
  → MaintenanceRuntimeCoordinator.run_for_turn(
        user_id, message,
        correlation_id=<turn cid>, thread_id=<conversation>,
        meaning=<compiled meaning>, world_entities=<observed entities>)
  → trace["maintenance"] = <bounded result>
```

The coordinator (`backend/app/cognition/maintenance_runtime.py`) holds
references to the SAME service instances the composition root already owns.
It is invoked from exactly two places:

1. `Cognition.process_turn` — once per conversational turn;
2. `POST /api/v10/maintenance/proposals/{id}/confirm` — the bounded depth-1
   re-audit after a confirmed, applied proposal.

It never subscribes to the EventBus, so no maintenance event can recursively
trigger maintenance.

A coordinator failure is caught in `process_turn`, reported as
`MAINTENANCE_FAILED` in the trace, and never blocks the user's reply.

## 3. Relevance gate

`MaintenanceRelevanceGate.evaluate()` is deterministic and explainable. It
consumes only canonical data the turn already produced:

| Trigger | Canonical signal |
| --- | --- |
| `STATE_CHANGE_SIGNAL` | compiled meaning created/proposed a material PREFERENCE/VALUE/GOAL/BOUNDARY/BELIEF/ASSUMPTION/COMMITMENT/DECISION/INTENT/CORRECTION/CONTRADICTION object |
| `CONFLICT_QUERY` | explicit conflict/consistency/prior-state phrasing (fixed, inspectable regex vocabulary) |
| `PREDICTION_OUTCOME` | a new OUTCOME/OBSERVATION object exists while canonical `predictions` are open, or an `incorrect` prediction has no `model_error_records` row |
| `UNKNOWN_RESOLUTION` | new FACT/OBSERVATION/CORRECTION/CLAIM evidence exists while `unknown_records` are OPEN |
| `DECISION_OUTCOME` | a new outcome object exists while canonical `decisions` are open |
| `WORLD_DEPENDENCY_CHANGE` | a world entity referenced by this turn is `stale=1` in the canonical World Model |
| `EXPLICIT_AUDIT_REQUEST` | explicit audit/inspect/maintenance phrasing |

The verdict is a structured `MaintenanceRelevance` (relevant, trigger kinds,
reasons[], relevant_domains[], confidence, bounded_checks[]) and is persisted
as a `maintenance.relevance_determined` event on the canonical bus for every
turn — including irrelevant ones, so "nothing ran" is itself observable.

Not used, by design: token frequency, random thresholds, model output, or
any hidden inference.

## 4. Bounded execution

- `SelfMaintenanceOrchestrator.audit()` gained optional, backward-compatible
  parameters: `families=` (deterministic narrowing to
  debt/contradictions/unknowns/model_errors/drift), `lifecycle=` and
  `thread_id=` (truthful surface stages). `audit()` with no new arguments is
  byte-for-byte the V10.0.1 full audit.
- One top-level invocation per turn: the coordinator calls `audit()` once,
  and the pre-existing `maintenance_runs.correlation_id UNIQUE` constraint
  makes retries return the persisted prior result.
- Duplicate findings collapse through the pre-existing fingerprint columns
  on `cognitive_debt`, `contradiction_records`, `unknown_records` and the
  open-proposal dedup in `MaintenanceProposalService.propose`.
- Every proposal created inside the bounded turn is surfaced in the turn's
  maintenance context: `run_for_turn` merges the audit's proposals with the
  exact rows the prediction-outcome and unknown-evidence matchers created
  through `MaintenanceProposalService.propose` (or deduplicated to),
  deduplicates by canonical proposal id, and reports
  `WAITING_FOR_CONFIRMATION` whenever at least one PROPOSED/DEFERRED
  proposal exists. Nothing is read from outside the turn's correlation and
  no second proposal store exists.
- Re-audit depth 1 is encoded in the correlation id (`<base>::reaudit1`):
  a suffix-marked correlation is refused by both `run_for_turn` and
  `reaudit_after_confirmation`, so the bound is provable from persisted data.
- No scheduler, no polling loop, no unbounded retries were added.

## 5. Surface behavior

`SurfaceLifecycle` and `CognitiveSurface` are reused unchanged. The V10 stage
vocabulary was already registered in `surface.py`'s `STAGES`; V10.1 emits it
only around work that executes:

- `AUDITING_PERSONAL_MODEL` wraps the audit (COMPLETED/FAILED honestly);
- `CHECKING_FOR_STALE_STATE`, `CHECKING_CONTRADICTIONS`,
  `CHECKING_OPEN_UNKNOWNS`, `COMPARING_PREDICTION_TO_OUTCOME`,
  `COMPARING_PERSONAL_STATE` wrap their respective family only when that
  family was selected;
- `ANALYZING_MODEL_ERROR` is emitted only when model errors were actually
  classified;
- `EVALUATING_MAINTENANCE_OPTIONS` only when proposal evaluation ran;
- `WAITING_FOR_CONFIRMATION` only when open proposals exist;
- `RE_AUDITING_MODEL` only during the bounded re-audit.

Irrelevant turns emit no maintenance stage at all. A failed audit leaves a
FAILED stage and a FAILED `maintenance_runs` row; snapshot status stays
FAILED. Surface emission failures never break maintenance work, and
maintenance never mutates state on surface failure (there is nothing to roll
back — stages are append-only events).

## 6. Conversation integration

`_summarize_trace` (main.py) now includes a `maintenance` block built by
`_summarize_maintenance()`: status, relevance verdict (with reasons),
finding summaries and open proposals. Every summary sentence is a fixed
deterministic label for a canonical classification (see
`maintenance_runtime.summarize_findings`), e.g.:

- TRUE_CONTRADICTION → "I found that this may conflict with an earlier
  recorded statement."
- VALUE_EVOLUTION → "This appears to be a change in priority rather than a
  direct contradiction."
- INSUFFICIENT_CONTEXT → "I don't have enough evidence to decide whether
  these statements refer to the same situation."

No chain-of-thought, no invented reasoning, no fake progress.

## 7. Confirmation and re-audit

The V10.0.1 authority chain is unchanged:

```
finding → evidence → proposal → explicit confirmation
       → AutonomyGovernor → PersonalStateService → new version
```

V10.1 adds one step at the API boundary: after
`POST /api/v10/maintenance/proposals/{id}/confirm` returns an APPLIED
proposal, the coordinator runs exactly one bounded re-audit under
`<base>::reaudit1` and the response gains an additive `reaudit` field.
Existing clients that read only proposal fields are unaffected. The re-audit:

- runs only the families the confirmed mutation could actually have changed,
  deterministically derived from the proposal type
  (`maintenance_runtime.REAUDIT_FAMILY_MAP`): e.g. a confirmed
  `RECORD_OUTCOME` re-audits `model_errors` + `debt`; `CONFIRM_UNKNOWN`
  re-audits `unknowns`; personal-state-mutating types (`RETIRE_ASSUMPTION`,
  `SUPERSEDE_OBJECT`, `WEAKEN_BELIEF`) include `drift` to verify the state
  transition. Unknown types fall back to (debt, contradictions, unknowns).
  The chosen families are reported in the `reaudit` payload and in the
  `maintenance.reaudit_started` event;
- reads the canonical current PersonalState version before running;
- is idempotent (UNIQUE correlation);
- refuses depth 2;
- reports failure inside `reaudit` without rolling back the applied
  canonical mutation.

Turn-level proposal presentation never auto-confirms anything.

### RECORD_OUTCOME application path

A confirmed `RECORD_OUTCOME` proposal is applied through the canonical
`PredictionEngine.observe()` — the single evaluation authority. The proposal
service (`MaintenanceProposalService._apply_record_outcome`):

1. resolves the target prediction from the proposal's evidence refs
   (`kind: prediction`), validated through the canonical user+tenant scope;
2. resolves the actual observation cognitive object from the evidence refs
   (`kind: cognitive_object`) via PersonalState — no observation, no apply;
3. passes the real observation text to `observe()` with no `supports`
   override, so the engine's explicit resolution-signal rules decide;
4. if the engine reports the evidence is insufficient (no explicit
   confirm/refute signal), the apply raises and the proposal is honestly
   `BLOCKED`: the prediction stays open, no verdict is fabricated, and the
   proposal is never falsely reported APPLIED;
5. on genuine resolution the engine itself updates the prediction row and
   emits `prediction.evaluated` / `prediction.correct|incorrect` (plus
   `surprise.detected` when applicable); the proposal service then resolves
   any linked UNVALIDATED_PREDICTION debt through the existing debt
   lifecycle. No outcome is duplicated into maintenance rows.

## 8. Event vocabulary

Three genuinely new event types on the canonical bus (registered in
`EVENT_TYPES`, labelled in `LABELS`):

- `maintenance.relevance_determined`
- `maintenance.reaudit_started`
- `maintenance.reaudit_completed`

Audit start/completion and proposal presentation reuse the existing
`cognitive_model.audit_started/completed` and `maintenance.proposed` events —
they were not duplicated.

## 9. Security boundary

Unchanged V8.5 chain: verified Principal → `uid()` → verified namespace →
`V10ScopedService._tenant()` (resolved from `auth_users`, never
caller-provided). The coordinator receives only the already-verified
`user_id` from `process_turn` / the confirm route. Cross-user access to
proposals, findings, re-audits and correlation snapshots is covered by
focused isolation tests (`test_v101_runtime_integration.py`, section G) in
addition to the whole V8.5/V9/V10 regression suites.

## 10. Portability boundary

No change. The V10.1 turn context (`run_for_turn`'s return value) is
transient runtime coordination state. Everything durable it touches —
findings, proposals, runs, health snapshots — already lives in the V10
tables that are already in the portability allowlist/domain map (including
`maintenance_runs`). No second package format, no new durable tables.

## 11. Health metadata (release marker)

`Runtime.health()` previously reported `release: "9.0.2"` while running the
V10.0.1 codebase. Compatibility decision:

- `version: "8.2"` — the established V8.2 API-contract marker — is
  preserved exactly;
- `release` keeps its existing name, type and position and now truthfully
  reports `"10.0.1"`, the released slice this branch builds on;
- `cognition.v10.runtime_integration: true` is an additive flag indicating
  the V10.1 runtime integration is active.

No field was removed or renamed; no client contract shape changed.

## 12. Frontend

Minimal additive changes only:

- `lib/types.ts`: `TurnMaintenance` type; optional
  `TurnCognition.maintenance`;
- `components/CognitiveSurface.tsx`: human labels for the (already
  server-emitted) V10 stages;
- `components/Chat.tsx`: `MaintenanceNotes` — renders canonical finding
  summaries and the open-proposal count inside the existing collapsed
  "Understanding" block, only when real maintenance produced real content.

No new navigation, no dashboard, no fake stages, no client-side invention.

## 13. Explicit non-features / unsupported

- No V11 Personal Laws.
- No background scheduler or polling for maintenance (interaction-driven
  only; the V8.3 `BackgroundCognition` remains what it was and does not
  invoke V10).
- Cognitive debt categories remain exactly the evidence-backed V10.0.1 set;
  no new categories were invented.
- `MODEL_STABILITY` requirements, local-model lock and CapabilityRouter
  behavior are untouched.
- The gate's phrase vocabularies are English; non-English conflict queries
  fall back to the canonical-object signals (A, C, D, E, F), which are
  language-independent.
