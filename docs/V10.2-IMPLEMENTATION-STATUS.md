# V10.2 implementation status — CORE foundation

## This checkpoint

Implemented a small evidence/governance foundation above (not beside) the released `CognitivePolicyEngine`:

- `PolicyEvidenceAssembler` is deterministic, read-only, correlation-scoped, and distinguishes adaptation from outcome evidence.
- `LearningSignalDeriver` emits only bounded `beneficial`, `neutral`, `harmful`, or `insufficient_evidence` signals; adaptation alone is never success.
- `PolicyGovernanceService` persists scoped candidates and append-only transition history, validates the lifecycle, emits structured `governance.transition` events, and retains correlation/reason/evidence references.
- `PolicyRuntimeCoordinator` is an explicit one-call-per-turn seam with no scheduler, recursion, global state, or auto-accept.

## Resolved CORE decisions

1. Effective policy remains `policies` + `CognitivePolicyEngine`. Governance uses additive `policy_governance` and `policy_governance_history` tables because the existing row cannot represent lifecycle/history without changing V8 semantics.
2. Constants are centralized in `governance.py`; this slice uses the released weak-evidence gate and fixed supported domains. No auto-accept exists: confirmation is required.
3. No new decision-guidance dimension is justified in this foundation slice.
4. MODEL_HANDLING is governance-only here; no capability is enabled and provider degradation remains owned by the existing provider/capability stack.
5. Canonical new event: `governance.transition`; legacy `policy.proposed`, `policy.updated`, and `policy.reverted` remain untouched.
6. `autonomy_preference` remains consumed by released code only; the governance layer does not bypass `AutonomyGovernor`.
7. Explicit instruction remains the existing engine's strong-evidence path; inferred evidence cannot silently become explicit authority.
8. Legacy policy deletion/revert semantics are unchanged; governance history stores candidate/value references and survives policy-row deletion.

## Verification

Targeted smoke coverage should exercise transition validation, append-only history, evidence provenance, insufficient evidence, and tenant/user scoping. Existing policy and V10.1 runtime suites remain the regression gate.

Known limitation: this is the CORE foundation only. Runtime adaptation proposal production, confirmation API/surface integration, portability package inclusion, and comprehensive dedicated V10.2 tests are the next slice.
