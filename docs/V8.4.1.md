# MEMORY//OS V8.4.1 — Experience → Skill → Principle

V8.4.1 turns learning from an event-log summary into persisted, evidence-backed
objects that can change future decisions:

```text
OBSERVATION → EXPERIENCE → SKILL CANDIDATE → VALIDATION → TRUSTED SKILL
             → RETRIEVAL → ARBITRATION → DECISION INFLUENCE → OUTCOME
             → REPUTATION → REFINEMENT

MULTIPLE EXPERIENCES / TRUSTED SKILLS → PRINCIPLE CANDIDATE → VALIDATION
             → TRUSTED PRINCIPLE → RETRIEVAL → DECISION INFLUENCE → OUTCOME
             → REPUTATION → REFINEMENT
```

Conversation remains the primary control surface. The Observatory is an
inspection surface over the same persisted state.

## Architectural decisions

V8.4.1 extends the systems already present in V8.3.1.2:

| Concern | Existing system reused | V8.4.1 extension |
|---|---|---|
| Evidence | `ObservationLog` | Every Experience references owned observation ids; observations remain canonical evidence |
| Learning | `LearningEngine` + background cycles | `KnowledgeService` adds evidence checks, candidate validation, promotion and maintenance; policy learning remains intact |
| Reputation | `ReputationStore` | Generic Skill/Principle counters were added to the same subsystem; confidence remains on the abstraction |
| Arbitration | `ArbiterV2` | `arbitrate_knowledge()` uses the same persistent arbitration ledger and events |
| Causality | `CausalGraph` | New node kinds `experience`, `skill`, `principle`, `usage`; no second graph |
| Decisions | `DecisionLog` | Learned influences create real usage records; resolved decisions create Experiences and resolve pending learned uses |
| Events | `EventBus` | V8.4.1 events were added to the canonical vocabulary |
| Context | `ContextBuilder` | Scope-checked Skill and Principle winners enter the bounded model context |
| Object permanence | `FocusTracker` | Experience, Skill and Principle are focusable stable-id objects |
| Conversation | model-selected cognitive tools | `list_learned`, `list_experiences`, `inspect_learned`, `correct_learned` call real subsystems |
| Background cognition | `BackgroundCognition` | A bounded `learning_patterns` task may create and validate candidates, but never promote them |
| Persistence | additive SQLite schema | `SCHEMA_V841`; V8/V8.1/V8.2/V8.3 tables are not replaced |

`ExperienceStore` is new because no existing object represented a structured,
meaningful episode connecting situation, action and observed outcome. It does
not duplicate observations or memory: it references observations and is used as
learning evidence.

`KnowledgeService` is new because the former `LearningEngine._propose()` emitted
summary events but did not persist operational Skills/Principles, evidence,
validation, use or lifecycle. It composes existing reputation, arbitration,
causality and events instead of reimplementing them.

## Experience

An Experience stores only fields used by the learning loop: situation, optional
intent/need/context, action, observation, outcome/consequences, success,
surprise/regret, confidence, scope, pattern key, source and provenance.

Creation requires at least one observation id owned by the same user. A
success/failure judgement requires an outcome. Validation requires:

- direct `OBSERVED` evidence;
- an action;
- an outcome.

Lifecycle:

```text
observed → enriched → validated → active → archived
```

Archive is also valid from earlier states. Every transition is written to
`experience_transitions` with reason and evidence ids and emitted on the event
bus.

A resolved `DecisionLog` decision creates an outcome observation and then an
Experience. The decision result still succeeds if the episode lacks enough
structure to validate; learning never gets to break outcome recording.

## Skill

A Skill is operational, not a sentence. It carries:

- name and statement;
- trigger and context;
- preconditions;
- ordered procedure;
- expected outcome;
- explicit scope;
- evidence/counterexamples;
- confidence, reputation and lifecycle;
- validation, usage, provenance and transition history.

A candidate requires linked Experiences. The deterministic validation policy
requires at least three successful validated/active Experiences, three distinct
observed origins, outcome consistency of at least 0.75, sufficient evidence
quality, coherent pattern evidence, valid operational structure and consistent
scope. Frequency by itself cannot pass.

Validation and promotion are separate calls. A passing candidate remains
`validating` until `promote()` verifies the latest persisted PASS record.

## Principle

A Principle uses the same audited abstraction infrastructure with stronger
checks. Normal promotion requires:

- at least two validated/live Skills;
- at least four successful Experiences across those Skills;
- at least two distinct Skill patterns;
- outcome consistency of at least 0.80;
- evidence quality of at least 0.60;
- generality of at least 0.50;
- scope consistency.

One Skill cannot validate a Principle. The higher-order detector only groups
already trusted Skills with the same explicit generalization hint and different
pattern keys. It is not “most frequent Skill = Principle.”

## Lifecycle, correction and forgetting

Skill and Principle lifecycle:

```text
candidate → validating → trusted → used → reinforced
                                  ↘ weakened → contradicted → retired
                                  ↘ outdated → retired
```

The exact path is evidence-dependent. A failed validation returns to candidate
unless counterevidence is strong enough to contradict it. Actual use first
moves an abstraction to `used`; an observed supported outcome reinforces it.
One contradictory use weakens it, two contradictory outcomes that outnumber
successes contradict it, and three failures with no success retire it.

Explicit corrections support:

- `weaken`;
- `contradict` / invalidate;
- `outdated`;
- `retire`, `forget`, `stop_using`;
- `rescope` / narrow.

Forgetting is a soft retirement. The row, evidence and audit trail remain, while
normal retrieval excludes it. Rescoping changes where it may be used and emits
the previous and new scope. A weakened, contradicted, retired, outdated or
rescoped Skill forces every dependent live Principle back through deterministic
validation; it cannot keep influencing decisions on stale supporting evidence.
A retired pattern is not silently recreated by background maintenance.

## Confidence is not reputation

**Confidence** answers: how strongly does evidence support this abstraction?
It is calculated during validation from evidence count, direct origins,
quality, consistency, counterexamples, structure, breadth and scope.

**Reputation** answers: how did this abstraction perform when actually used?
It starts `INSUFFICIENT EVIDENCE` with a null score. Retrieval does not change
it. Use without an observed outcome does not change it. `SUPPORTED` or
`CONTRADICTED` without evidence is downgraded to `INSUFFICIENT EVIDENCE`.

The fields remain separate in persistence, APIs, context and the Observatory.

## Retrieval, arbitration and future decisions

Only `trusted`, `used`, `reinforced` and `weakened` abstractions are eligible.
Before scoring, retrieval checks:

1. user namespace;
2. lifecycle;
3. task/project/domain/environment scope;
4. recorded preconditions against explicitly supplied current-world state.

Every declared Skill precondition needs at least 0.8 content-token support from
that current-world bundle with matching negation polarity. Query wording cannot
satisfy a world precondition; empty or explicitly contradicted state blocks use.

The canonical arbiter scores relevance, confidence, reputation, scope, source
authority, specificity, recency and current-world match. Failure history and a
weakened lifecycle apply explicit penalties. Reputation has enough weight for a
slightly less similar reliable abstraction to beat an exact but poorly
performing match.

A winner enters `ContextBuilder` as operational guidance. User instructions,
permissions, safety, autonomy rules and current world state remain authoritative.
Entering the bounded response context records a real usage and causal edge; a
mere retrieval does not.

## Causal and outcome loop

Promotion writes provenance edges:

```text
experience → skill
experience / skill → principle
```

Use writes:

```text
skill / principle → decision
```

A resolved use writes:

```text
outcome → skill / principle
```

`DecisionLog.resolve()` finds pending learned uses that actually influenced the
same decision and resolves them from the supplied outcome. This updates
reputation and lifecycle through `KnowledgeService`; no score is invented.

## Safe background learning

`BackgroundCognition` gained one bounded task:

```text
learning_patterns
```

It looks for validated successful Experiences with the same explicit pattern
key and coherent actions. It may create a Skill candidate and run deterministic
validation. It may similarly identify higher-order patterns across trusted
Skills. It **never promotes** a candidate. The cycle records real findings or an
honest empty list through the existing background tables and events.

## Conversation and object permanence

The real-model tool path gained:

| Tool | Purpose |
|---|---|
| `list_learned` | Skills/Principles with lifecycle, confidence, reputation, scope and evidence counts |
| `list_experiences` | Meaningful episodes and their evidence counts |
| `inspect_learned` | Evidence, provenance, validation, lifecycle and usage summary |
| `correct_learned` | Weaken, contradict, outdate, retire/forget, or rescope the focused object |

The model chooses these tools; V8.4.1 adds no keyword dispatcher. Tool arguments
are bound to the server-side user id. Skill and Principle focus uses stable ids,
so “forget that skill” and “is that still valid?” can resolve without requiring
the user to quote an id. Ambiguous focus is refused.

Explanations provide evidence-backed summaries only. They explicitly state that
private chain-of-thought is not exposed.

## Observatory

The **Experience → Skill → Principle** panel reads:

- `GET /api/experiences`;
- `GET /api/skills`;
- `GET /api/principles`;
- per-item explanation endpoints.

It displays lifecycle, confidence, reputation, scope, evidence,
counterexamples, usage and latest validation. Selecting a Skill/Principle sets
backend focus for conversational follow-ups. The panel has no fixture data and
no client-side learning state.

## Persistence

V8.4.1 adds:

- `experience_transitions`;
- `knowledge_items`;
- `knowledge_evidence`;
- `knowledge_validations`;

All reads and writes include `user_id` where ownership is relevant. Evidence
links are validated against the same namespace. Schema creation is additive and
runs after `SCHEMA_V83`.

## Deliberate limitations

- Pattern detection is deterministic and conservative. It uses explicit pattern
  metadata and coherent observed actions; it is not a general semantic research
  engine.
- There is no scheduler daemon. Background learning runs only when an existing
  bounded background cycle is invoked.
- Global promotion is refused from ordinary per-user evidence unless provenance
  explicitly marks a global-authorized source.
- Authentication remains outside this slice. `user_id` is a namespace boundary,
  not production identity/authentication.
- Demo mode can exercise all deterministic learning behavior, but natural tool
  selection needs a real tool-calling model and is reported separately.
