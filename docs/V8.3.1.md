# MEMORY//OS V8.3.1 — Conversational Cognition

V8.3 built the cognitive subsystems. V8.3.1 lets you *talk* to them.

This is not a new feature family and not a redesign. It closes one gap: the
subsystems existed but the conversation could not reach them.

## The problem this release fixes

At V8.3 the agent had five tools, all about memory. Missions, world state,
predictions, attention, continuity, history and simulation were reachable only
over HTTP or through the Observatory.

So this happened:

> **You:** What missions am I currently working on?
> **V8.3:** *(searches memory, finds a note about a project, improvises)*

The mission registry held the answer. The model never saw it. Worse, when the
model had nothing it produced something plausible — the single largest source
of invented state in the system.

V8.3.1:

> **You:** What missions am I currently working on?
> **V8.3.1:** *(calls `list_missions` against the real registry)*
> "One: Finish the quarterly report — active, 0% progress. No next step is
> recorded for it."

The full audit of where the wiring was missing is in
[V8.3.1-AUDIT.md](V8.3.1-AUDIT.md).

## What changed

### 1. Cognitive tools (`backend/app/agent/cognitive_tools.py`)

Fifteen tools that call the real subsystems — no second implementation of
anything, each a thin adapter over `runtime.cognition.*`:

| Tool | Subsystem | For questions like |
|---|---|---|
| `list_missions` | `MissionRegistry` | "what missions do I have" |
| `get_mission` | `MissionRegistry` | "what's the next step" |
| `create_mission` | `MissionRegistry` | "start tracking X" |
| `update_mission_state` | `MissionRegistry` | "pause that", "mark it done" |
| `add_mission_step` | `MissionRegistry` | "the next thing is Y" |
| `complete_mission_step` | `MissionRegistry` | "I finished the first part" |
| `get_mission_blockers` | `MissionRegistry` | "what's blocking me" |
| `get_world_state` | `WorldStateV2` | "what projects am I working on" |
| `get_world_changes` | `WorldStateV2` | "what changed" |
| `get_current_focus` | missions + world + continuity | "where did we leave off" |
| `get_predictions` | `PredictionEngine` | "what do you expect" |
| `get_attention_state` | `AttentionEngineV2` + background | "anything I should know" |
| `get_historical_state` | `TimeMachine` | "what did you know last week" |
| `simulate_scenario` | `SimulationEngine` | "what if I delay this" |
| `explain` | missions + world + observations | "why?", "what changed?" |

They are added in `MemoryAgent._tools_for`, the one place both the model path
and the deterministic planner build their toolset — so every cognitive call
gets the same MODEL_CALL / TOOL_DECISION / TOOL_RESULT / MODEL_REVISION /
FINAL_RESPONSE tracing that memory tools already had (§15), with no new tracing
code.

### 2. Routing is the model's decision

No keyword matching on the real path. The tool descriptions and the system
prompt tell the model what each subsystem holds and that *a memory, a goal, a
mission, a commitment and a project are different objects*; the model chooses.
The only pattern matching is in the deterministic fallback, where there is no
model to decide (§3/§16).

### 3. Missions are first-class context (§4)

`ContextBuilder` gained a `mission` section, ranked first in the prompt. Open
missions are carried even when the message is unrelated — the assistant should
know what you are in the middle of. `next_step` is rendered as either
`next step (RECORDED): …` or `NO NEXT STEP RECORDED`, so the prompt itself
cannot blur the difference.

### 4. No invented next steps (§5)

The heart of the release. Every mission projection carries
`next_step_status`, one of:

- `RECORDED` — a real step exists, quote it;
- `NO_NEXT_STEP_RECORDED` — say so, and if you suggest something, label it a
  proposal.

Tools return `NO_MISSIONS_RECORDED`, `NO_BLOCKERS_RECORDED`,
`NO_CHANGES_RECORDED`, `HISTORY_NOT_AVAILABLE`, `NOTHING_RECORDED` rather than
empty structures that invite improvisation. Absence is information.

### 5. Object permanence (§8)

`FocusTracker` already refused to guess between ambiguous references — good
logic, but only ever written by the Observatory. Now the conversation drives it:

- `mission`, `goal`, `project`, `person`, `simulation` and `observation` joined
  the focusable kinds (previously `set_focus(..., "mission", ...)` raised
  `ValueError`, which is exactly why "pause that" could not work);
- any cognitive tool touching an object sets focus on it, keyed by `thread_id`;
- mutating tools resolve a missing id through focus, then a single open
  mission, and otherwise return `AMBIGUOUS_REFERENCE` listing the candidates
  so the assistant asks instead of guessing.

Identity resolution is by stable id, never by matching display text.

### 6. Truth labelling (§10)

Everything reaching the model is tagged: missions and steps `RECORDED`, world
state and changes `OBSERVED`, predictions `PREDICTED`, simulations `SIMULATED`,
and model suggestions must be labelled as proposals. The prompt forbids
restating any of the latter as established fact.

## The vocabulary, precisely (§27)

These are genuinely different objects in different tables. Asking about one
must not be answered from another.

| Object | What it is | Stored in | Truth status |
|---|---|---|---|
| **Memory** | Something you told the system, durable | `memories` | RECORDED |
| **Goal** | An outcome you want | `world_entities` (kind=goal) | OBSERVED |
| **Mission** | A tracked objective with state, steps, blockers, progress | `missions` | RECORDED |
| **Commitment** | Something you owe someone, usually dated | `world_entities` (kind=commitment) | OBSERVED |
| **Project** | An ongoing body of work | `world_entities` (kind=project) | OBSERVED |
| **World state** | Current tracked reality, with freshness | `world_entities` | OBSERVED |
| **Observation** | Raw evidence, promotable to memory only explicitly | `observations` | OBSERVED |
| **Prediction** | An expectation about the future | `predictions` | PREDICTED |
| **Simulation** | A what-if against a frozen snapshot | `sandbox_runs` | SIMULATED |
| **Proposal** | The assistant's suggestion | not stored | PROPOSED |

A goal is a wish; a mission is a wish with machinery. "Run a marathon" is a
goal. "Follow the 16-week training plan, currently week 3, blocked on a knee
injury" is a mission.

## What is NOT claimed

- Conversational cognition covers the subsystems listed above. Documents and
  connectors remain METADATA ONLY / NOT CONNECTED, as in V8.3.
- The explanation engine reports recorded evidence. It does not expose model
  reasoning, and where evidence is thin it says `INSUFFICIENT EVIDENCE`.
- There is still no authentication. `user_id` is a namespace, not an identity.
- The deterministic fallback understands missions, but it is a pattern matcher
  and labels itself `DETERMINISTIC FALLBACK` in every reply.

# V8.3.1.1 — Conversational Mission Action Reliability

A reliability refinement discovered during real-model verification of V8.3.1.
Same branch, no API changes, no new endpoints, no UI redesign.

## Why

With a real `llama3.2:3b`, "Resume it." after pausing a mission produced a
reply claiming the state was unknown. The registry was correct; the *tool
surface* was the problem. `update_mission_state` required the model to choose a
state enum, write a reason and know to omit `mission_id` — too many
simultaneous decisions for a small local model. See `V8.3.1-AUDIT.md` for the
full diagnosis.

## The four action tools

| Tool | Arguments | Target | Valid from |
|---|---|---|---|
| `pause_mission` | `mission_id?`, `reason?` | `paused` | active, waiting, blocked, draft |
| `resume_mission` | `mission_id?`, `reason?` | `active` | paused |
| `complete_mission` | `mission_id?`, `reason?` | `completed` | any open state |
| `abandon_mission` | `mission_id?`, `reason?` | `abandoned` | any open state |

Both arguments are optional on every tool. Omitting `mission_id` is the normal
case: the mission is resolved from conversational focus. Toolset 15 → 19,
registered through the existing `_tools_for()` so both the real and fallback
paths get them with automatic tracing.

### Resolution order (unchanged from V8.3.1)

explicit `mission_id` → focused mission for this session → the sole open
mission → otherwise a structured failure. **The tool never guesses.**

### Return statuses

| Status | Meaning |
|---|---|
| `UPDATED` | A real transition happened; includes `previous_state`. |
| `NO_CHANGE` | Already in the target state (`reason_code`: `ALREADY_PAUSED` / `ALREADY_ACTIVE` / `ALREADY_COMPLETED` / `ALREADY_ABANDONED`). No history row written. |
| `TERMINAL_STATE` | Completed / failed / abandoned. Not reopened. |
| `INVALID_TRANSITION` | E.g. resuming a blocked mission. |
| `AMBIGUOUS_REFERENCE` | Several candidates (up to 5 listed). Nothing mutated. |
| `NO_MISSIONS_RECORDED` / `NOT_FOUND` | No such mission. |

Every successful transition goes through the canonical
`MissionRegistry.set_state()`, so `mission.paused` / `mission.resumed` /
`mission.completed` / `mission.abandoned` are emitted by the registry itself,
with correlation ids and evidence preserved.

## What is NOT claimed

- The model is not routed by keywords. `graph.py` contains no NL command
  dispatch on the real-model path; deterministic planning exists only in the
  clearly labelled demo fallback.
- Completion is never inferred from reported progress. `complete_mission` runs
  only on an explicit user request.
- A next step is never invented. Missions without one report
  `NO NEXT STEP RECORDED`.
- A state change is never narrated unless the tool result confirms it.

- **Full fast backend suite**: 627 passed, 10 skipped, 6 deselected in 344.9 s

- **Frontend**: `npm ci`, `typecheck`, `lint`, `build` all exit 0.

# V8.3.1.2 — null-tolerant tool arguments and focus-driven action selection

Two defects that only a real model could reveal. Both were found on an actual
Ollama `llama3.2:3b`; both are fixed and re-verified on the same model.

## Problem A — `list_missions` rejected the model's own argument

```
TOOL_DECISION list_missions
TOOL_FAILED   ValidationError: ListMissionsArgs.open_only
              Input should be a valid boolean  [input_value=None]
```

The model emitted `{"open_only": null}`, meaning "I have no value for this
optional argument". That is reasonable; the schema rejected it and the user saw
a failed tool call.

**Fix, at the schema boundary.** A `_NullTolerant` Pydantic base drops any
explicit `null` for a field that has a default, so the default applies. Every
optional argument schema now inherits it, because the same thing can happen to
`mission_id`, `reason` or any other optional field. `open_only` is additionally
typed `bool | None` and normalised inside the tool body.

`true` and `false` behave exactly as before. `null` is now identical to
omitting the argument. A read still never invents or mutates a mission.

## Problem B — the model would not select `resume_mission`

With a focused, paused mission and the message "Resume it.", the real model
selected `get_mission` and `get_world_state`, never reached `resume_mission`,
and the mission stayed paused.

**The cause was missing context, not bad routing.** Conversational focus was
tracked and was used by `_resolve_mission()` at tool-execution time, but it was
never serialised into the prompt. The model was told "a paused mission exists"
by the missions section and "you may act on the mission under discussion" by
the tool descriptions, but nothing told it *which* mission was under discussion
or what state it was in. With no id in hand the only rational move is to go
looking for one — hence `get_mission`, then `get_world_state`. The model was
behaving sensibly given what it could see.

**Fix: serialise the focused object.** The context bundle gained a `focus`
section, rendered first:

```
IN FOCUS RIGHT NOW (what 'it'/'that' refers to):
- FOCUSED MISSION (this is what 'it', 'that' and 'this mission' refer to):
  'Ship the billing migration' [state=paused] id=ms_7c6cd96a57d3;
  valid lifecycle actions right now: resume_mission, complete_mission,
  abandon_mission. Act on it directly with the matching lifecycle tool and
  omit mission_id — do NOT call get_mission or get_world_state first.
```

The valid-action list is derived from the mission's real recorded state via
`_LIFECYCLE_ACTIONS`, mirroring the registry's own transition rules, so the
prompt can never advertise a transition the registry would refuse. A terminal
mission offers no actions and says so. A focus entry whose mission no longer
exists is omitted rather than advertised.

The SYSTEM_PROMPT gained a matching "ACTING ON THE FOCUSED OBJECT" policy, and
the tool descriptions were sharpened: `get_mission` and `get_world_state` now
say explicitly that they are not part of a lifecycle change, and
`complete_mission_step` says it is not a lifecycle tool at all.

**This is still not keyword routing.** No substring test, no regex, no dispatch
from user text. `graph.py` is unchanged on the real-model path apart from the
prompt text, and a test asserts no `"resume" in ...` style routing exists
there. The model still chooses the tool; it simply can now see what it is
choosing about.

### A note on prompt cost

The first version of these descriptions was verbose and pushed the prompt to
~3,950 tokens. On this CPU-only machine that is ~11 minutes of prompt
processing per model call, and the turn hit the 900 s timeout and degraded to
the deterministic fallback — which produced a correct-looking answer for the
wrong reason. The descriptions were tightened to ~3,330 tokens. The lesson is
recorded because it is easy to mistake a timeout for a routing failure: always
check `provider` and the activity trail for `PROVIDER_DEGRADED`.
