### 1.1 SSRF / network security (`test_v843_net_security.py`, 36 tests)

Verified BLOCKED, with the correct reason code, for: loopback IPv4/IPv6,
private IPv4 ranges (10/8, 172.16/12, 192.168/16), link-local (169.254/16,
including the cloud metadata address 169.254.169.254), IPv6 loopback/
link-local/unique-local/multicast, IPv4-mapped IPv6 (`::ffff:127.0.0.1`),
alternate IPv4 literal encodings (decimal `2130706433`, hex `0x7f000001`,
octal, partial-dotted `127.1`), unsafe URL schemes (`ftp://`,
`javascript:`), userinfo in the URL, disallowed ports, multicast, CGNAT
(100.64.0.0/10), and the unspecified address (`0.0.0.0`). DNS rebinding
(`http://localhost/` resolving to `::1`) is blocked at the post-DNS
resolution stage via a real system resolver call, not a mock. A local
`ThreadingHTTPServer` fixture with a narrowly-scoped `allow_loopback`
monkeypatch (permitting only `127.0.0.1` and widening the allowed port
range) is used to test fetch *mechanics* — oversized response,
redirect-loop, unsupported content-type, and timeout handling — without
weakening the real SSRF policy tested everywhere else in the file.

### 1.2 Research engine integration (`test_v843_research_engine.py`, 18 tests)

Against a local fixture HTTP server exposing distinct routes: full session
lifecycle; a failed fetch (404) is persisted honestly (`sources`/`fetches`
show `UNREACHABLE`/`FETCH_FAILED`, and finishing the session reports
`FAILED`, never silently hidden); an empty page produces zero fabricated
evidence; an SSRF-blocked URL is recorded in the fetch ledger rather than
discarded; evidence carries full provenance (`source_id`, `fetch_id`,
`locator`, `content_hash`); claim confidence is capped at ≤0.55 for a
single source; fetching two pages from the *same* domain does **not**
count as independent corroboration; two claims disagreeing on a factual
value are both preserved as `contested` with a `research_conflicts` row
referencing both; a page containing prompt-injection-style text is flagged
in `injection_flags` but the flagged text is never treated as an
instruction; proposing then applying a world update requires
`confirm=True`, caps confidence at ≤0.60, leaves the World Model untouched
until applied, and rejects a second apply with `ValueError`; research
evidence never creates a memory/skill/principle row; every accessor
(`get`, `sources`, `fetches`, `evidence`, `claims`, `get_claim`) is
isolated per user; the session source limit is enforced honestly; and
`status()` states plainly that no search engine exists.

### 1.3 Real live network (`test_v843_live_network.py`, 5 tests)

These tests perform **genuine** outbound calls with no mocking:

- `https://example.com/` fetched for real → `COMPLETED`, HTTP 200, a real
  SHA-256 content hash, real latency, real byte count.
- A full `ResearchEngine` session run against that same live page — a real
  fetch, real (possibly zero, honestly reported) evidence extraction, a
  real session finish.
- `https://httpbin.org/redirect-to?url=http://127.0.0.1/secret` — a real
  request to a real public redirecting server whose `Location` header
  points at a private address; the redirect is followed and then
  correctly **blocked** (`PRIVATE_ADDRESS`), proving per-hop re-validation
  against a live, uncontrolled redirector, not a local simulation.
- A request to a domain that genuinely does not resolve
  (`this-domain-truly-does-not-exist-memoryos-v843.invalid`) reports
  `FETCH_FAILED` / `DNS_RESOLUTION_FAILED` — a real DNS failure, never
  converted into "no information found."
- A final self-check test always runs and honestly reports whether the
  rest of the file's tests were live-verified or skipped; in this
  environment outbound network access was confirmed available
  (`socket.create_connection(("example.com", 443))` succeeded), so all
  five tests executed for real rather than being skipped.

### 1.4 DB migration (`test_v843_migration.py`, 2 tests)

A real SQLite file is built using **only** the pre-V8.4.3 schema strings
(`SCHEMA` + `SCHEMA_V83` + `SCHEMA_V841` + `SCHEMA_V842`), then populated
with one representative row each in `memories`, `missions`,
`world_entities`, `world_changes`, `knowledge_items`,
`explanation_snapshots`, and `cognitive_events` — a genuine V8.4.2-shaped
database. Sanity-checked to confirm the new tables do not yet exist.
Opening this file through the real `Database.__init__` startup path (the
same path `app.main` uses) is then proven to: (a) create all seven new
`research_*` tables, (b) leave every pre-existing row byte-identical
(including newly-additive columns like `world_entities.freshness_class`
appearing with their default value, never altering existing data), and (c)
allow a brand-new `ResearchEngine` to operate immediately against the
migrated file. A second test proves re-opening the now-migrated file a
second time is idempotent (no duplication, no corruption).

### 1.5 API / tools / explanation integration (`test_v843_api_and_tools.py`, 11 tests)

Full HTTP lifecycle via FastAPI's `TestClient` against the real app,
dependency-overriding only the `Runtime` (never mocking the research
engine, database, or network layer): create session → fetch (against a
local fixture server, loopback-widened only for this test file) → sources
→ fetches → evidence → claims → conflicts → finish → list. World-update
`propose`/`apply` is verified to require `confirm=True` (a `confirm=false`
call returns HTTP 400). Cross-user access returns 404. A direct SSRF
attempt (`169.254.169.254`) through the API layer returns `BLOCKED`. The
legacy `/api/research` route is proven unchanged
(`provider_state == "RESEARCH PROVIDER NOT CONFIGURED"`, `state ==
"BLOCKED"`). `build_cognitive_tools()` is proven to register all six new
tools with names matching the spec, and `start_research` →
`fetch_research_source` → `inspect_research_claims` /
`inspect_research_evidence` are exercised end to end via their raw
LangChain tool functions. Tool descriptions are asserted to contain the
honesty language ("never invent [a URL]", "no search engine"). Finally,
`ExplanationEngine.explain(subject_kind="research_claim", ...)` is proven
to return `explanation_type == "RESEARCH_EVIDENCE"` with a
`claim_confidence` decisive factor whose description states the value is
capped, and an unknown research subject id falls back to the existing
`INSUFFICIENT EVIDENCE` path rather than fabricating an explanation.

## 3. Live browser/API QA (real processes, not TestClient)

A real `uvicorn` backend (`0.0.0.0:8000`) and a real `next start` frontend
(`0.0.0.0:3000`) were run together and exercised through the same-origin
`/api/*` Next.js proxy exactly as a browser would:

1. `GET /api/research/v2/status` → `available: true`, honest "no
   search-engine integration" detail text.
2. `POST /api/research/v2` → new `DRAFT` session created.
3. `POST /api/research/v2/{id}/fetch` with `https://example.com/` → a
   **real** internet fetch → `COMPLETED`, HTTP 200, 559 bytes, 2 evidence
   excerpts extracted, 2 claims created.
4. `POST .../world-updates/propose` then `POST
   .../world-updates/{id}/apply` with `confirm: true` → the World Model
   gained a new entity; confirmed via `GET /api/world` that the entity
   carries `"source": "research"` and the same capped confidence
   (`0.388`) as the proposed update — visibly distinguishable from a
   user-stated fact.
5. Separately, `POST .../fetch` with `http://169.254.169.254/latest/meta-data/`
   and `http://127.0.0.1:1/` both returned `{"status": "BLOCKED",
   "error_code": "PRIVATE_ADDRESS", ...}` through the full live
   browser-facing proxy path — SSRF defense is not bypassed by going
   through the Next.js rewrite layer.
6. Server-rendered HTML of `/observatory` was confirmed to contain the
   "Connected Research" panel title, proving the panel renders in the
   actual page output (not just compiles).

All demo/QA data generated during this verification pass was removed
before packaging (`backend/data/*.sqlite3*`, `backend/data/chroma/`), and
these paths are excluded from the release ZIP regardless via
`.gitignore`/the release script's exclusion list.

## 5. Known limitations (honest, not gaps hidden as passes)

- **Real Ollama model path: NOT VERIFIED IN THIS ENVIRONMENT.** No local
  Ollama server was reachable. V8.4.3's own correctness does not depend on
  live LLM tool selection — every new tool, route, and pipeline stage was
  exercised directly and via a real running FastAPI process — but the
  claim "a real model will choose `start_research`/`fetch_research_source`
  unprompted" is not verified here, consistent with the same limitation
  already documented for V8.4.1/V8.4.2.
- **No search engine.** By design — URLs must be supplied explicitly.
- **Deterministic, not semantic, claim/conflict extraction** — documented
  as such in `docs/V8.4.3.md` and in the `research.py` module docstring.
- **Source quality is a static heuristic**, not a live reputation/authority
  service.
