# MEMORY//OS V8.5 — Production Trust, Auth, Privacy, Multi-User, Observability

V8.5 turns the single-user local-first cognitive system into a
production-trustworthy multi-user system without weakening the cognitive
architecture. It extends the existing SQLite persistence layer, the canonical
cognitive EventBus, the Runtime composition root, the FastAPI application and
the Observatory. It does not create a second database, a second event bus,
parallel identity state, parallel memory storage, or a second audit system.

## Architecture

```text
existing SQLite database
          │
          ├── SCHEMA_V85 (additive): tenants, auth_users, auth_sessions
          │
          ├── IdentityService (app/security/identity.py)
          │     ├── PBKDF2-HMAC-SHA256 password hashing (600k iterations)
          │     ├── 256-bit session tokens, stored ONLY as SHA-256 hashes
          │     ├── login / logout / expiry / revocation / rotation
          │     └── tenant + role management, legacy-namespace adoption
          │
existing EventBus ◄── auth/authz/session/rate-limit/admin audit events
existing Runtime  ◄── identity + Metrics + RateLimiter + readiness()
FastAPI app       ◄── one trust middleware: request id, auth, CSRF,
                       rate limits, body bounds, latency metrics, safe errors
Observatory       ◄── SecurityPanel + SystemHealthPanel
```

## The identity ↔ namespace mapping

Every cognitive table has keyed rows by `user_id` since V8. V8.5 makes that
column the enforcement boundary instead of adding a new one:

- each `auth_users` row owns exactly one unique, server-generated `namespace`;
- when `AUTH_MODE=required`, the namespace for a request is resolved ONCE,
  from the verified session, in `uid()` — caller-supplied `user_id` values in
  query strings or bodies are ignored everywhere;
- cognitive tools are built server-side bound to the principal's namespace;
  no tool accepts a user/tenant/namespace argument, so the model cannot
  escape its caller's namespace;
- object routes addressed by a bare id (`/api/memories/{id}`,
  `/api/cognition/turn/{id}`, `/api/execution/{id}`,
  `/api/arbitration/{id}`) verify ownership and answer 404 on mismatch, so
  guessed IDs reveal neither data nor existence.

No cognitive row is rewritten by any of this. `AUTH_MODE=disabled` (default)
preserves V8.4.1–V8.4.4 behavior exactly: one anonymous local principal in the
demo namespace, no login surface.

## Tenancy model

`tenant → users → cognitive namespaces`. Self-registration gives the FIRST
account the default workspace (`ten_default`) with the `owner` role — this is
the deterministic adoption point for a migrated V8.4.4 database. Every later
self-registered account receives its own fresh workspace. Admin-created
accounts join the admin's workspace. Tenants are never implicitly shared.

## Roles and permissions (least privilege)

| Permission            | member | admin | owner |
|-----------------------|:------:|:-----:|:-----:|
| cognition.read/write  |   ✓    |   ✓   |   ✓   |
| portability.export    |   ✓    |   ✓   |   ✓   |
| portability.restore   |   ✓    |   ✓   |   ✓   |
| research.run          |   ✓    |   ✓   |   ✓   |
| health.read           |   ✓    |   ✓   |   ✓   |
| security.read         |        |   ✓   |   ✓   |
| users.manage          |        |   ✓   |   ✓   |
| roles.manage          |        |       |   ✓   |

There is no unrestricted admin: managing an account never grants access to
its cognitive data, admins cannot grant admin/owner roles, and owners cannot
disable or demote themselves.

## Authentication

- Registration validates email shape and password length (10–256).
- Passwords are hashed with PBKDF2-HMAC-SHA256 (configurable iterations,
  default 600,000). No plaintext or reversible storage.
- Login failure is uniform for unknown accounts, wrong passwords and disabled
  accounts — no account-existence oracle — and burns comparable hashing time
  for absent accounts.
- Sessions: 256-bit random tokens delivered both as an `HttpOnly` +
  `SameSite=lax` cookie (`Secure` in production) and as a bearer token for
  API clients. Only SHA-256 hashes are stored. Every login mints a new token
  (no fixation); logout, admin revocation and account disablement all kill
  sessions; expiry is enforced server-side.
- CSRF: cookie-authenticated mutations require the `X-CSRF-Token` header
  matching the per-session CSRF token (constant-time compare). Bearer-token
  requests are CSRF-exempt by design.
- The identity provider is an abstraction (`IdentityService`); routes never
  touch password or token internals, so the provider can evolve (e.g. OIDC)
  behind the same interface.

## Migration from V8.4.4

Deterministic and idempotent:

1. Reopen the same database under V8.5 — `SCHEMA_V85` is additive, all
   V8.4.4 rows are untouched (verified by `test_v85_migration.py`).
2. The first registered account (workspace owner) calls
   `POST /api/admin/migrate-legacy-namespace`. Their account's namespace
   pointer moves to the legacy single-user namespace (`demo-user` by
   default). No cognitive row is rewritten.
3. Repeat calls return `{"migrated": false, "reason": "already_adopted"}`.
   A second account attempting adoption receives 409.

## Rate limiting

Sliding-window, in-process, per principal (per client address for anonymous
auth attempts). Categories: `auth`, `api`, `research`, `portability`,
`expensive` (chat/sandbox/perceive). Violations return 429 with `Retry-After`,
increment metrics and emit `security.rate_limited` on the canonical bus.
Enabled by default when `AUTH_MODE=required`; scope is honestly single-process.

## Observability

- **Request correlation**: every request gets/echoes `X-Request-ID`; error
  bodies carry it; log lines can carry it.
- **Metrics** (`GET /api/metrics`, `health.read`): request counts, status
  classes, auth failures, authorization denials, rate-limit hits, per-route
  latency histograms. Labels are route templates and coarse categories —
  never memory text, emails, namespaces or tokens.
- **Structured logs**: `LOG_JSON=1` emits single-line JSON, redacted through
  a secret-shape filter.
- **Health**: `/api/health/live` is liveness only; `/api/health/ready`
  reports per-dependency truth — `ACTIVE / DEGRADED / NOT_CONFIGURED /
  BLOCKED / FAILED` — with 503 when a required dependency failed. The demo
  provider reports NOT_CONFIGURED, not fake health.

## Audit

All security events are canonical `cognitive_events` rows emitted through the
existing EventBus: `auth.registered`, `auth.login`, `auth.logout`,
`auth.failed`, `session.revoked`, `session.expired`, `authorization.denied`,
`permission.changed`, `user.created`, `user.disabled`, `export.accessed`,
`security.rate_limited`, `security.suspicious_request`, `admin.action`.
Payloads contain identifiers and coarse metadata only; emails appear redacted
(`a***@example.com`); credentials and tokens never appear.

## Error handling

Stable error envelope on every non-2xx response:

```json
{"error": {"code": "FORBIDDEN", "message": "...", "request_id": "req_..."},
 "detail": "...", "request_id": "req_..."}
```

`detail` is preserved for V8.4.4 clients. Codes are stable
(`VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`,
`PAYLOAD_TOO_LARGE`, `RATE_LIMITED`, `CSRF_REJECTED`,
`DEPENDENCY_UNAVAILABLE`, `INTERNAL_ERROR`). Unhandled exceptions log full
redacted detail server-side and return only the envelope — no stack traces,
no file paths.

## Portability and research under multi-user

Export/import/restore inherited per-owner scoping from V8.4.4 and now run
under the authenticated principal: packages belong to a namespace, foreign
packages fail validation with an explicit ownership error, restore re-checks
authorization, download is audited (`export.accessed`), and the endpoints are
rate-limited. Research sessions, sources, fetches, evidence and claims remain
namespace-scoped; external evidence cannot cross tenants.

## Production configuration gate

`PRODUCTION=1` makes startup FAIL unless `AUTH_MODE=required`, CORS origins
are explicit, secure cookies are on and the PBKDF2 cost is sane. A deployment
cannot silently start in an insecure configuration.

## Honest limitations

- Rate limiting and metrics are in-process (single instance). Multi-instance
  deployments need shared stores; the surfaces say so.
- Password auth is the only built-in provider; `IdentityService` is the seam
  for OIDC/SSO.
- The demo Next.js frontend does not include a login page; in required mode
  clients authenticate via the API (bearer or cookie+CSRF). The Observatory
  renders the honest session state either way.
- TLS termination is the deployment's responsibility; `COOKIE_SECURE`
  assumes HTTPS in production.
- LangGraph checkpoints are keyed by thread id; V8.5 closes cross-user reads
  by refusing foreign thread ids at `/api/chat` and gating checkpoint reads
  by conversation ownership.
