# V8.3.1 pre-work audit — where the conversation loses the cognitive systems

Traced `POST /api/chat` through the real code at commit `b3fc6b5`.

## The actual path

```
POST /api/chat  (main.py:73)
  │
  ├─ correlation_id = turn_<12hex>
  │
  ├─ cognition.process_turn(...)          ← observational side-channel
  │     intent → need → world.observe → prediction → attention → continuity
  │     Builds understanding. Its results are NOT passed to the agent.
  │
  └─ agent.run(user_id, thread_id, message, correlation_id)
        load_context  → ContextBuilder.build()  → 10 sections
        agent node    → model.bind_tools(build_memory_tools(...))
        tools node    → 5 memory tools only
        memory_manager → response
```

## Gap 1 — the agent has five tools, all about memory

`agent/tools.py::build_memory_tools` returns exactly:
`search_memory`, `save_memory`, `update_memory`, `delete_memory`,
`consolidate_memory`.

`MissionRegistry`, `WorldStateV2`, `PredictionEngine`, `AttentionEngineV2`,
`ContinuityEngine`, `TimeMachine` and `SimulationEngine` are **not reachable by
the model at all**. Every V8.3 subsystem is API- and panel-only.

Consequence: asked *"what missions am I working on?"*, the model can only call
`search_memory`. It gets semantically similar memories, not mission objects —
and then writes a plausible-sounding answer from them. This is the single
biggest source of invented facts in V8.3.

## Gap 2 — the system prompt only describes memory

`SYSTEM_PROMPT` (graph.py:33) mentions memory tools exclusively. Even once
cognitive tools exist, the model needs to be told these objects are distinct
from memories (§19/§20).

## Gap 3 — the context builder has no mission section

`ContextBuilder.build()` assembles: memory, episodic, goal, commitment, world,
intent, preference, decision, prediction, capability. **No mission.** Grep for
`mission` in `context_builder.py` returns only unrelated `permission` matches.

So even mission-relevant turns carry zero mission state into the prompt (§4).

## Gap 4 — `process_turn` understanding is discarded

The cognitive loop computes intent, need, world updates, predictions and
attention on every turn, then the agent runs independently of it. The two
halves share only a `correlation_id`. Nothing the loop understood reaches the
model.

## Gap 5 — focus is UI-driven, not conversational

`FocusTracker` (V8.2 §21) is genuinely good: 30-minute TTL, refuses ambiguous
references instead of guessing, distinguishes typed ("that mission") from bare
("that") references.

But it is keyed by `session_id` and only written by `POST /api/focus` from the
Observatory. **Chat never sets focus and never resolves against it.** So "pause
that mission" cannot work conversationally (§8).

Note the key is `(user_id, session_id, subject_kind)` — one row per *kind*, so
a mission and a memory can be focused simultaneously; bare references correctly
become ambiguous.

## Gap 6 — no next-step truthfulness boundary

`missions.next_step` is nullable and nothing distinguishes a recorded next step
from a model suggestion. With no mission data in context at all, the model
currently fills the gap with invention — exactly what §5 forbids.

## What must NOT be rebuilt

- `FocusTracker` — extend to thread-keyed conversational use, keep the
  resolution logic.
- `MissionRegistry`, `WorldStateV2`, `TimeMachine`, `SimulationEngine`,
  `PredictionEngine`, `AttentionEngineV2` — all work; they need exposure, not
  reimplementation.
- `ContextBuilder` — add a mission section, do not rewrite.
- `run_tool_safely` / `ExecutionTrace` — already emit MODEL_CALL,
  TOOL_DECISION, TOOL_RESULT, MODEL_REVISION, FINAL_RESPONSE (§15 is
  already satisfied once cognitive tools flow through the same path).

## Environment note (new in this release)

Ollama **is installed and running** in this environment for the first time:
`llama3.2:3b` pulled, generating, and confirmed to emit real `tool_calls` from
natural language. It required 6 GB of swap (the box has ~2 GB RAM) and runs at
roughly 45 s–2.5 min per tool-calling turn on CPU. Real-agent tests must budget
for that.

# V8.3.1.1 addendum — the defect real-model testing found

V8.3.1 shipped with its conversational layer verified by a real `llama3.2:3b`.
Continued real-model use then exposed one concrete failure in a five-turn
conversation:

```
1. Create a mission to finish the next MEMORY//OS milestone...   OK
2. What missions am I currently working on?                      OK
3. What is the next step?                    OK (NO NEXT STEP RECORDED)
4. Pause that mission.                                           OK
5. Resume it.                    FAILED — "current state is unknown"
```

## What was NOT broken

`MissionRegistry.set_state()`. Called directly with
`state="active", reason=..., mission_id=<paused id>` it performed
`paused → active`, returned `status="UPDATED"`, `previous_state="paused"`, and
emitted `mission.resumed`. The registry and its event vocabulary were correct
and are unchanged by this release.

## The actual cause

The only way to change mission state conversationally was the generic
`update_mission_state(state, reason, mission_id, blocked_reason, waiting_on)`.
That asks a 3B model to do three things at once: recognise the intent, map it
to the right enum value, and invent a reason string — while also deciding to
omit `mission_id` so focus can resolve it. The model reliably recognises the
verb "resume" but not that argument bundle, so the call was either malformed or
skipped, and the model then narrated an unknown state.

In other words: the tool surface asked the model to do the subsystem's job.

## The fix, and what it deliberately is not

Four action tools — `pause_mission`, `resume_mission`, `complete_mission`,
`abandon_mission` — each taking only two optional arguments. The model picks
the verb; the tool supplies the object (via the existing focus resolution), the
target state and a default reason.

This is **not** keyword routing. Nothing in `graph.py` inspects the user's
message on the real model path. The improvement is entirely in tool design:
fewer decisions per call, and each tool named after an intention rather than a
mechanism.

All four funnel into one private `_transition` helper that calls the canonical
`MissionRegistry.set_state`, so events, evidence, history and progress are
unchanged. `update_mission_state` is retained for `blocked` and `waiting`,
which the action tools do not cover.

## Truthfulness rules added with them

- **no-op ≠ transition.** Resuming an already-active mission returns
  `NO_CHANGE` / `ALREADY_ACTIVE` and writes no history row.
- **terminal states are not reopened.** Resuming a completed, failed or
  abandoned mission returns `TERMINAL_STATE` with the real state, and offers a
  new mission instead of resurrecting the old one.
- **invalid transitions explain themselves.** Resuming a *blocked* mission
  returns `INVALID_TRANSITION`, because blocked is not paused.
- **ambiguity still mutates nothing.** Two paused missions and no focus returns
  `AMBIGUOUS_REFERENCE` with both candidates listed.

## A second defect found during this round's browser QA

Browser QA of this exact build surfaced an unrelated, pre-existing bug: the
`voice` artwork in `components/Gallery.tsx` computed SVG geometry with
`Math.sin` and emitted unrounded floats, whose last digit differed between the
server render and the client, producing a React hydration mismatch on every
page. Fixed by rounding to 3 decimal places. This had nothing to do with
cognition; it was simply never caught because earlier rounds could not run
browser QA.

# V8.3.1.2 addendum — two defects only the real model could find

## A. The schema rejected a reasonable model call

`list_missions` failed with a Pydantic ValidationError on
`{"open_only": null}`. Small models emit explicit nulls for optional arguments
routinely. Treating that as a hard error turns a well-formed call into
TOOL_FAILED.

Fixed at the boundary: a `_NullTolerant` base drops nulls for fields that have
defaults, so null == omitted. Applied to every optional argument schema, not
just the one that happened to fail, because the failure mode is general.

## B. Focus was tracked but never shown to the model

This is the more interesting one, and it was misdiagnosed twice.

V8.3.1.1 concluded the problem was argument complexity and added four
single-purpose action tools. That was a real improvement, but the real model
*still* picked `get_mission` and `get_world_state` for "Resume it.".

The actual gap: `FocusTracker` was consulted at tool-EXECUTION time, inside
`_resolve_mission()`, but was never serialised into the prompt at tool-SELECTION
time. So the model knew a paused mission existed (from the missions section)
and that it could act on "the mission under discussion" (from the tool
descriptions), but it was never told which mission that was, or its state. With
no id available, looking one up is the correct inference. The model was not
being stupid; it was under-informed.

The fix serialises the focused object — id, title, real state, and the
lifecycle actions valid from that state — as the first context section. The
valid-action set is derived from the recorded state, so the prompt cannot
suggest an impossible transition, and a terminal mission is explicitly labelled
as not reopenable.

**General lesson for this codebase:** state that only affects execution is
invisible to tool selection. If the model must make a decision that depends on
some piece of state, that state has to be in the prompt, not merely available
to the tool that runs afterwards.

## C. A timeout can masquerade as a fix, or as a failure

The first V8.3.1.2 attempt made the descriptions very explicit, pushing the
prompt to ~3,950 tokens. On this CPU-only box that exceeded the 900 s timeout;
the turn degraded to the deterministic fallback, which performed the correct
transition and printed a plausible answer. A less careful reading of that run
would have recorded a pass. The trace showed `provider used: ollama` but the
activity contained a degradation notice and the answer carried the
DETERMINISTIC FALLBACK label.

Always check, in this order: `provider` has no `(degraded)` suffix, the answer
carries no fallback label, and `TOOL_DECISION` plus `TOOL_RESULT` for the
expected tool are both present.
