# MEMORY//OS V10.1 — Cognitive Self-Maintenance Runtime Integration

## Status

Planning specification for the next milestone after the released V10.0.1 Cognitive Self-Maintenance core.

Branch:
`feature/v10.1-runtime-integration`

Baseline:
`main` at the released V10.0.1 state.

V10.1 is a runtime-integration milestone. It does not replace the V10 core, redesign MEMORY//OS as a dashboard, or introduce V11 Personal Laws.

## 1. Objective

V10.0.1 provides deterministic Cognitive Self-Maintenance services:

- Cognitive Debt
- proposition-aware Contradiction Engine
- explicit Unknowns
- Model Error
- Cognitive Health
- confirmation-gated Maintenance Proposals
- canonical EventBus integration
- V9/V10 portability
- V8.5 authorization/isolation

V10.1 connects those capabilities to the normal MEMORY//OS interaction loop so maintenance is part of the operating system rather than a collection of callable APIs.

North-star behavior:

```
CONVERSATION
  ↓
UNDERSTAND
  ↓
CHECK PERSONAL MODEL
  ↓
ASSESS MAINTENANCE RELEVANCE
  ↓
DETECT / CLASSIFY ONLY WHEN RELEVANT
  ↓
SHOW SAFE LIVE COGNITIVE ACTIVITY
  ↓
PROPOSE BOUNDED MAINTENANCE
  ↓
USER CONFIRMATION
  ↓
CANONICAL STATE UPDATE
  ↓
RE-AUDIT
  ↓
CONTINUITY
```

## 2. Architectural principles

V10.1 MUST:

1. Reuse V9 canonical PersonalState, Cognitive Objects, EventBus, SurfaceLifecycle, Prediction/Outcome, Causality, Learning, Autonomy Governor, Portability, and V8.5 security boundaries.
2. Preserve immutable historical state.
3. Keep deterministic authority at the canonical boundary.
4. Preserve UNKNOWN / INSUFFICIENT_CONTEXT / INSUFFICIENT_EVIDENCE rather than guessing.
5. Require explicit confirmation for material personal-state maintenance.
6. Avoid hidden chain-of-thought exposure.
7. Avoid a second memory, identity, event, or state system.
8. Avoid a generic dashboard as the primary experience.
9. Avoid an autonomous scheduler in this milestone unless an explicitly bounded, opt-in mechanism is proven necessary and separately specified.
10. Make maintenance proportional to relevance; the system should not continuously interrupt the user with findings.

## 3. Scope

### 3.1 Runtime integration

Connect `SelfMaintenanceOrchestrator` to the existing conversation/runtime path.

The runtime should be able to:

- determine whether the current turn can materially interact with the personal model;
- invoke bounded maintenance checks when relevant;
- attach maintenance observations/findings to the current interaction correlation;
- return safe maintenance activity through the existing EventBus / SurfaceLifecycle;
- avoid duplicate audits during one turn;
- remain idempotent under retries.

The runtime integration must not execute destructive maintenance implicitly.

### 3.2 Relevance gate

Introduce a deterministic maintenance-relevance policy before invoking expensive or noisy V10 checks.

Examples of relevant signals:

- a turn changes or questions a stored preference, value, goal, boundary, belief, assumption, commitment, or decision;
- the user explicitly asks whether something changed or conflicts with prior statements;
- a new outcome materially bears on a recorded prediction;
- new observations can resolve an explicit unknown;
- a previously open decision now has an outcome;
- a known world dependency becomes stale relative to canonical evidence.

Relevance must be explainable.

Irrelevant conversational turns should not cause a full maintenance audit.

### 3.3 Live cognitive surface

Use the existing V9 SurfaceLifecycle and V10 surface vocabulary.

Real states may include:

```
AUDITING_PERSONAL_MODEL
CHECKING_FOR_STALE_STATE
COMPARING_PERSONAL_STATE
CHECKING_CONTRADICTIONS
CHECKING_OPEN_UNKNOWNS
COMPARING_PREDICTION_TO_OUTCOME
ANALYZING_MODEL_ERROR
EVALUATING_MAINTENANCE_OPTIONS
WAITING_FOR_CONFIRMATION
APPLYING_VERIFIED_UPDATE
RE_AUDITING_MODEL
```

Requirements:

- surface activity starts when work actually starts;
- activity is correlated to the current interaction;
- completion/degradation/failure is persisted through the existing event stream;
- the UI never claims a cognitive stage that did not occur;
- no private chain-of-thought is exposed;
- stale activity cannot remain permanently ACTIVE after terminal failure/completion.

### 3.4 Conversation integration

The response pipeline should be able to summarize relevant maintenance findings in natural language without exposing implementation internals.

Examples:

- “I found that this conflicts with an older preference.”
- “This looks more like a change in priority than a contradiction.”
- “I do not have enough evidence to decide whether these statements refer to the same situation.”
- “Your earlier prediction now has an observed outcome.”
- “I found an open question that this new information may resolve.”

These are user-facing summaries derived from canonical findings, not invented model reasoning.

### 3.5 Confirmation workflow

Material state changes must remain confirmation-gated.

Required flow:

```
FINDING
  ↓
EXPLANATION + EVIDENCE
  ↓
PROPOSAL
  ↓
USER CONFIRMS / REJECTS / DEFERS
  ↓
AUTONOMY GOVERNOR
  ↓
PERSONAL STATE TRANSITION
  ↓
RE-AUDIT
```

A finding-resolution action that only closes a finding must remain distinct from a personal-state change.

### 3.6 Re-audit

After a confirmed material update:

- re-load the canonical state;
- verify the intended transition occurred;
- re-run only the relevant bounded maintenance checks;
- record the resulting state/finding relationship;
- preserve the prior state version.

A re-audit must not recursively trigger an unbounded maintenance loop.

## 4. Runtime control model

The V10.1 runtime should use a bounded control object similar to:

```
MaintenanceTurnContext
- correlation_id
- user_id
- tenant_id
- conversation_id
- trigger_kind
- relevance
- relevant_domains
- audit_budget
- findings
- proposals
- terminal_state
```

This is a runtime coordination structure, not a persistent second source of truth.

Suggested trigger kinds:

- STATE_CHANGE_SIGNAL
- CONFLICT_QUERY
- PREDICTION_OUTCOME
- UNKNOWN_RESOLUTION
- DECISION_OUTCOME
- WORLD_DEPENDENCY_CHANGE
- EXPLICIT_AUDIT_REQUEST

## 5. Bounded execution

V10.1 must prevent maintenance storms.

Per interaction:

- at most one top-level maintenance invocation;
- relevant service families should be narrowed deterministically;
- duplicate finding fingerprints should collapse within the same correlation;
- no recursive self-triggering from maintenance events;
- re-audit must have a finite depth of 1 for a normal confirmed update;
- terminal states must always be emitted.

The existing CapabilityRouter / tool-surface narrowing and local-model lock remain unchanged.

## 6. Event model

Reuse the canonical `cognitive_events` stream.

V10.1 may extend event vocabulary only when needed for runtime observability.

Possible events:

- `maintenance.turn_started`
- `maintenance.relevance_determined`
- `maintenance.audit_started`
- `maintenance.audit_completed`
- `maintenance.proposal_presented`
- `maintenance.reaudit_started`
- `maintenance.reaudit_completed`

Every event must contain:

- verified user identity context;
- tenant scope;
- correlation ID;
- subject kind/id where applicable;
- bounded safe payload;
- no hidden reasoning trace.

## 7. Error and degradation handling

V10.1 must distinguish:

- no maintenance needed;
- maintenance completed with no findings;
- maintenance completed with findings;
- maintenance degraded because an optional capability was unavailable;
- maintenance failed;
- user decision pending.

A failed optional surface update must not roll back a successful canonical state transition.

A failed maintenance audit must not mutate personal state.

## 8. Security

Reuse V8.5:

- verified Principal;
- `uid()` namespace mapping;
- cognition read/write permissions;
- user + tenant scope;
- existing CSRF/session/rate-limit/audit boundaries.

Never trust user-provided tenant IDs as authority.

Any canonical V9 lookup used during runtime maintenance must be scoped through the established identity boundary.

## 9. Portability

No second export/import system.

V10.1 runtime coordination state should be transient unless a persistence requirement is demonstrated.

Only durable findings/proposals/outcomes that already belong to V10 canonical tables should be exported.

If new durable runtime records are introduced, they must:

- be explicitly specified;
- be included in the existing portability allowlist/domain map;
- preserve user/tenant scope;
- preserve references;
- support deterministic validation and restore.

## 10. UI direction

Primary experience remains conversation-first.

The user should experience:

```
SPEAK / TYPE
    ↓
MEMORY//OS WORKS
    ↓
VISIBLE SAFE ACTIVITY
    ↓
RESPONSE / FINDING / PROPOSAL
```

Do not introduce:

- a permanent V10 dashboard;
- a new left navigation hierarchy for every maintenance feature;
- fake real-time traces;
- decorative “AI brain” animations that do not reflect real state;
- manual operation of every V10 service.

Advanced inspection may remain available through Observatory/developer surfaces.

## 11. Real-world examples

### Example A — preference evolution

User says:

“I used to prefer stability, but now I want to explore more.”

Expected behavior:

- detect a potentially changed VALUE/PREFERENCE state;
- compare against canonical prior object(s);
- classify VALUE_EVOLUTION when justified;
- show evidence;
- propose the canonical state transition;
- wait for confirmation;
- apply through PersonalStateService;
- re-audit.

### Example B — unrelated correction

A correction targets an older object about work.

A separate object states a coffee preference.

The correction must not be treated as superseding the coffee preference.

### Example C — prediction outcome

A previously recorded prediction gets an observed outcome.

Expected behavior:

- detect PREDICTION_OUTCOME relevance;
- record/evaluate Model Error when warranted;
- update maintenance/health evidence;
- do not infer instability from one event;
- preserve historical prediction and outcome records.

### Example D — uncertain conflict

User statements appear inconsistent but scope or proposition identity is unclear.

Expected behavior:

- return INSUFFICIENT_CONTEXT;
- explain what is missing;
- do not create a TRUE_CONTRADICTION record solely from shared tokens.

### Focused runtime

Add tests for:

- relevance gate;
- no-op irrelevant turn;
- one bounded maintenance invocation;
- correlation propagation;
- duplicate finding collapse;
- terminal lifecycle;
- degraded/failed runtime behavior;
- confirmation gate;
- re-audit depth limit;
- no recursive maintenance storm;

### Regression

Run:

- V10 focused suite;
- V9 semantic/conversation/security/portability regression;
- V8.5 security/auth/isolation/migration;
- V8.4.4 portability;
- full backend non-slow suite.

### Frontend

Run:

- npm ci;
- typecheck;
- lint;
- production build.

### Browser

Browser verification must be reported as PASS, FAIL, or NOT VERIFIED.

Do not substitute static build results for browser evidence.

### Real model

Real-model evidence must be reported exactly as:

- PASS
- FAIL
- NOT VERIFIED
- NOT CONNECTED
- DEGRADED

Deterministic tests cannot be reported as real-model verification.

## 14. Non-goals

V10.1 does not implement:

- Personal Laws;
- Identity Evolution;
- Personal Worldline;
- unrestricted autonomous scheduling;
- opaque agentic authority;
- automatic deletion of personal history;
- psychological or medical inference;
- a large maintenance dashboard;
- a parallel memory graph.

## 15. Success definition

V10.1 succeeds when a normal MEMORY//OS conversation can cause the system to notice a materially relevant change, conflict, unresolved question, or prediction outcome, visibly represent the real maintenance work, explain the evidence, safely propose a canonical update, wait for user control, apply the approved transition, and re-audit without losing historical continuity or creating maintenance noise.

## 16. Long-term transition

V10.0.1 established:

**the model can detect and represent maintenance needs.**

V10.1 establishes:

**the operating loop can use that maintenance capability during real interaction.**

V11 can then build on a runtime that knows how to safely maintain the model.
