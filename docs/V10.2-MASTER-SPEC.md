# Evidence-Governed Adaptive Cognitive Policy

Baseline: released V10.1.0 mainline (`main`).
Branch: `feature/v10.2`.
Revision: 2 — corrected after architecture audit against the released

## 1. Status

**SPECIFICATION ONLY. Nothing in this document is implemented.**

This document defines the next bounded architectural layer after V10.1. It
introduces no runtime code, no tables, no endpoints, no migrations, no
frontend changes, and no behavior changes. Every statement about future
behavior is a requirement on a future implementation phase, not a claim
about the current system. Where this document describes the existing
system, the wording has been audited against the released V10.1.0 code and
states only what is actually implemented.

The current system (V10.1.0) provides, verified and released:

```
OBSERVE → AUDIT → DETECT → CLASSIFY → PROPOSE → UPDATE → RE-AUDIT
```

V10.2 extends this loop into:

```
OBSERVE → EVALUATE → MODEL ERROR / CONSEQUENCE → LEARNING SIGNAL
→ CANDIDATE POLICY CHANGE → EVIDENCE CHECK → GOVERNOR
→ EXPLICIT CONFIRMATION WHEN REQUIRED → CANONICAL POLICY UPDATE
→ FUTURE TURN INFLUENCE → MEASURE → RE-EVALUATE
```

## 2. Thesis

MEMORY//OS must not only remember what happened. When — and only when —
evidence is sufficient, it should be able to adapt bounded rules about
how its own future cognitive behavior operates — with the same discipline
the system already applies to memory: evidence before inference, explicit
lifecycle instead of silent drift, user authority before autonomy, and
measurable consequences instead of claimed improvement.

**V10.2 is a governance layer, not a new policy engine.** The system
already has a behavioural policy authority: the V8.2
`CognitivePolicyEngine`, which owns the current effective policy values
that shape conversational behavior. What the system cannot yet do is
justify policy adaptation from **cross-system learning evidence** —
evaluated predictions, classified model errors, decision outcomes,
intervention outcomes — under an explicit governed lifecycle with
confirmation gating, supersession, expiry, and measured effectiveness.
That governance capability is V10.2:

- **V8.2 `CognitivePolicyEngine` = CURRENT POLICY AUTHORITY.** It owns
  what the effective policy *is*, today and after V10.2.
- **V10.2 = EVIDENCE-GOVERNED POLICY EVOLUTION / GOVERNANCE LAYER.** It
  decides *when* existing policy evidence is sufficient for adaptation,
  *when* a change becomes a candidate, *when* a candidate requires
  confirmation, *how* changes are scoped, superseded, and expired, *how*
  future outcomes are measured, *how* conflicting evidence is handled,
  and *how* adaptation effectiveness is evaluated.

There are no two competing policy authorities anywhere in this design.
Every statement in this specification is subordinate to that boundary.

## 3. Definitions

### 3.1 The existing V8.2 `CognitivePolicyEngine` (implemented today)

`backend/app/cognition/policy_engine.py` is the released, canonical,
adaptive behavioural policy authority. Verified facts about it:

- It owns eight bounded behavioural dimensions, each with a fixed value
  vocabulary and default: `response_depth` (brief/balanced/detailed),
  `clarification_frequency` (low/normal/high), `interruption_tolerance`
  (low/normal/high), `planning_preference` (none/light/structured),
  `recommendation_preference` (options/single/none), `autonomy_preference`
  (ask_first/act_low_risk/act), `explanation_density`
  (minimal/normal/verbose), `silence_tolerance` (low/normal/high).
- It persists current policy state in the existing `policies` table.
- It already provides: `get()`, `list()`, `learned()`, `effective()`,
  `observe()`, `revert()`, `apply_utterance()`, `explain()`.
- Its evidence model is already implemented: `STRONG = 0.9` (explicit
  user utterance, applied immediately), `WEAK = 0.25` (inferred from
  behaviour), `WEAK_EVIDENCE_REQUIRED = 3` (a weak signal must repeat
  three times before it changes anything), `MIN_CONFIDENCE_TO_APPLY =
  0.45` (below it, a learned value does not take effect).
- It already emits canonical events on the one EventBus:
  `policy.updated`, `policy.proposed`, `policy.reverted`.
- Behavioural dimensions are always revertible through `revert()`, which
  restores the effective dimension to its default by **deleting the
  current `policies` row** (`DELETE FROM policies WHERE user_id=? AND
  key=?`). The released implementation does NOT preserve that policy row
  as historical state; the canonical EventBus still records the revert
  (`policy.reverted`, with the prior and default values in the payload).
  V10.2 does not alter this released legacy behavior.

The released `LearningEngine` (`learning.py`) also reads/writes the same
`policies` table through `set_policy()`, `get_policy()`, `policies()`,
and `revert_policy()`, and performs pattern mining (`consolidate()`) that
can set policy values. (Audit note: **both released legacy revert paths
delete their current `policies` row** — `CognitivePolicyEngine.revert()`
via `DELETE ... WHERE user_id=? AND key=?`, and
`LearningEngine.revert_policy()` via `DELETE ... WHERE id=?`. Their event
behavior differs: the former emits `policy.reverted`, the latter emits
`policy.updated`. This is pre-existing released behavior; V10.2 neither
uses nor changes these legacy deletion semantics. V10.2 governance
history requirements must therefore handle references to `policies` rows
that may later be deleted through either legacy path; see §22 Open
Question #9.)

**Therefore V10.2 MUST NOT define a peer or replacement policy engine.**

### 3.2 V8.2 CognitivePolicyEngine vs V10.2 Policy Governance Boundary

| Concern | Existing V8.2 | V10.2 |
| --- | --- | --- |
| Current effective policy | **YES** — `effective()` over the `policies` table is the single source of truth | **NO** — never stores or computes a competing effective value |
| Explicit user preference | **YES** — `apply_utterance()` / `observe()` with STRONG evidence, applied immediately | May consume it as evidence context; never intercepts it |
| Weak-signal accumulation | **YES** — WEAK × `WEAK_EVIDENCE_REQUIRED` before change | May add cross-system evidence classes (§6.B); never bypasses the accumulation rules |
| Cross-system learning signal (predictions, model errors, outcomes) | **NO / limited** — not part of the V8.2 evidence vocabulary | **YES** — the core V10.2 contribution |
| Policy proposal governance (lifecycle, scope, supersession, expiry) | **LIMITED** — `policy.proposed` event + confidence gating, no governed lifecycle | **YES** — the governed adaptation lifecycle (§8) |
| Confirmation gating for new adaptation | **LIMITED** — STRONG applies immediately; weak signals apply at threshold without explicit confirmation | **YES** — §9 confirmation matrix for cross-system-evidence adaptations |
| Future policy influence on turns | **YES** — existing consumers read `effective()` today | Governs *how adaptation occurs*; influence itself flows through the existing engine and consumers |
| Outcome measurement (did the adaptation work?) | **LIMITED** — evidence in, no effectiveness loop | **YES** — §12 measurement architecture |
| Action authorization | **NO** | **NO — AutonomyGovernor**, unchanged, for both |
| Skill/Principle creation | **LearningEngine** (existing) | **NO** — consumes by reference only |
| EventBus | **YES** — `policy.proposed/updated/reverted` are canonical | **REUSES** — additive governance events only (§4.4) |
| Current policy storage | **`policies` table** | **MUST REUSE / EXTEND additively — never replace** (§4.3) |

### 3.3 Adaptive Cognitive Policy adaptation (the V10.2 unit)

The V10.2 unit of work is not a new kind of policy object; it is a
**governed adaptation** of behavioural policy: a scoped, versioned,
evidence-backed, user-confirmable proposal-to-change (or newly justified
tendency in a new V10.2 domain, §5.4), whose acceptance is applied
*through* the existing canonical authorities and whose effect is then
measured. A governed adaptation:

- is **evidence-backed**: references the canonical cross-system evidence
  (§6.B) and/or the existing V8.2 evidence (§6.A) that justifies it; an
  adaptation with zero evidence references is invalid by construction;
- is **explicitly scoped**: verified user + tenant, exactly one policy
  domain (§5), a declared target inside that domain (for the three
  existing-dimension domains: an existing `CognitivePolicyEngine`
  dimension and target value from its fixed vocabulary), and optionally a
  context scope and temporal validity window;
- is **lifecycle-controlled** by the new governance lifecycle (§8) —
  which is explicitly a *future* concept layered above, never a rewrite
  of, the existing engine's current-policy state;
- is **auditable**: creation, transitions, consultations and
  effectiveness observations are events on the one EventBus with
  correlation IDs;
- is **reversible where applicable**: rollback flows through the existing
  `revert()` path plus governance supersession; irreversible external
  actions are never made permissible by any adaptation (§9);
- is **measurable** (§12): declares expected effect and measurement plan
  at proposal time;
- is **bounded to the supported domains** (§5): no free-form
  natural-language rule is ever an adaptation target;
- is **separate from raw memory** and **separate from Skills/Principles**
  (§13); and
- is **subordinate to deterministic authority rules**: the
  AutonomyGovernor, the V8.5 identity boundary, the V8.2 engine's own
  validation rules (`MIN_CONFIDENCE_TO_APPLY`, weak-signal accumulation),
  and the confirmation chain always outrank it.

### 3.4 Epistemic states (never collapsed)

Every assertion V10.2 handles carries exactly one epistemic state. These
states are orthogonal to both the existing V8.2 current-policy state and
the new governance lifecycle (§8), and MUST NOT be merged into either:

| State | Meaning |
| --- | --- |
| OBSERVED | An event actually happened and was captured in a canonical record at the time it happened (e.g. an evaluated prediction row, an autonomy disposition in the trace). |
| RECORDED | A statement was explicitly stored on user authority (e.g. a STRONG policy utterance), independent of whether the system observed it happen. |
| INFERRED | Derived deterministically from OBSERVED/RECORDED material by an explainable rule; carries its derivation. |
| PREDICTED | A forward-looking expectation with confidence; not evidence of anything until evaluated. |
| PROPOSED | A candidate change offered for explicit decision; has no behavioral effect. |
| ACCEPTED | Explicitly confirmed by the user (or auto-accepted only where §9 explicitly allows); not yet necessarily applied or consulted. |
| ACTIVE | Currently applied (via the existing engine for existing dimensions) and eligible to influence future turns. |
| SUPERSEDED | Replaced by a newer version; retained, never deleted. |
| EXPIRED | Temporal validity or evidence freshness ran out; retained. |
| REJECTED | Explicitly declined; retained, and the rejection is itself evidence. |
| UNKNOWN | The system cannot determine the state from available evidence and says so; UNKNOWN is a reportable answer, never silently coerced to any other state. |

Rules: an INFERRED statement never silently becomes OBSERVED; a PREDICTED
statement never becomes evidence until evaluated against an OBSERVED
outcome (the existing `PredictionEngine.observe()` discipline);
PROPOSED never has runtime influence — only ACTIVE does; UNKNOWN is
always presentable to the user and to Cognitive Health.

### 3.5 Existing terms reused unchanged

Meaning Kernel, cognitive objects, PersonalState (versioned), EventBus,
ExecutionTrace, PredictionEngine, observation/outcome records,
ModelErrorService, Experience → Skill → Principle learning
(`LearningEngine`), Attention Engine (`AttentionEngine` /
`AttentionEngineV2`), AutonomyGovernor (dispositions ACT / ASK / WAIT /
DO_NOTHING / BLOCKED), Cognitive Debt, Contradiction Engine, Unknowns,

existing meaning and remain authoritative in their domains.

## 4. Architecture

### 4.1 Reuse of existing authorities (mandatory)

| Concern | Existing authority (reused, not duplicated) |
| --- | --- |
| **Current effective behavioural policy** | **`CognitivePolicyEngine` / `policies` table — the single policy authority** |
| Policy pattern mining & Skills/Principles | LearningEngine (Experience → Skill → Principle) |
| Meaning of a turn | Meaning Kernel / cognitive objects |
| Personal facts and preferences | PersonalStateService (versioned) |
| Event record | The one EventBus (incl. existing `policy.*` events) |
| What actually executed | ExecutionTrace |
| Forward expectations & evaluation | PredictionEngine (`observe()` remains the single evaluator) |
| Model failure classification | ModelErrorService |
| Intervention timing | Attention Engine (`AttentionEngine` / `AttentionEngineV2`) |
| Action authorization | AutonomyGovernor |
| Model-content hygiene | V10 Cognitive Debt / Contradictions / Unknowns / Health |
| Turn-scoped bounded execution | V10.1 MaintenanceRuntimeCoordinator patterns |
| Proposal/confirmation infrastructure | V10 maintenance proposal infrastructure, where sufficient (§4.3) |
| Identity/tenant | V8.5 boundary, exactly |
| Export/import | Existing portability architecture |

### 4.2 Explicitly forbidden constructs

V10.2 MUST NOT create: a peer or replacement policy engine; a competing
active-policy store; a parallel policy database; a shadow PersonalState;
a second EventBus or second event stream; a second identity model; a
hidden reward model; an opaque reinforcement-learning loop; an autonomous
scheduler; a background daemon; an independent learning memory; a second
learning engine; duplicate Skills or Principles; a second attention
engine; or a hidden chain-of-thought store. Any implementation found to
contain one of these fails acceptance regardless of test results.

### 4.3 Storage rule (binding default for the implementation phase)

The default architectural assumption is:

1. **Reuse the existing `policies` table and `CognitivePolicyEngine`**
   for current effective policy. V10.2 adds no competing store.
2. **Extend additively only when necessary** (the V8.2 precedent: the
   confidence/evidence columns were themselves an additive V8.2
   migration).
3. **Prefer the existing EventBus and the existing V10 maintenance
   proposal infrastructure** for proposal records, governance decisions
   and audit history, where those structures are sufficient.
4. A new persistent structure is allowed **only** if the CORE-phase
   architecture review proves the existing canonical stores cannot
   represent the required lifecycle or evidence **without corrupting
   existing semantics** — and the review's reasoning must be recorded.
5. A new structure, if ever approved, **must never become a second source
   of truth for current effective policy.**

The resulting separation of concerns is fixed regardless of the storage
outcome:

```
CURRENT EFFECTIVE POLICY        → existing CognitivePolicyEngine / policies table
POLICY CHANGE PROPOSAL /
GOVERNANCE EVIDENCE             → existing canonical proposal/event infrastructure
                                  where possible
POLICY HISTORY                  → canonical event/history infrastructure
```

No competing active-policy store, under any storage decision.

### 4.4 EventBus boundary

The existing policy events are already canonical: `policy.proposed`,
`policy.updated`, `policy.reverted`. V10.2 reuses the one EventBus and
these events where they already express the fact (e.g. an applied
adaptation of an existing dimension surfaces as the engine's own
`policy.updated`). Where the future implementation needs new events
(e.g. governance-lifecycle transitions, consultation records,
effectiveness observations), they must be explicitly identified as
**additive V10.2 governance events** — registered in the existing
`EVENT_TYPES` discipline, never replacements for the existing `policy.*`
vocabulary, and never a second stream.

### 4.5 New governance components (implementation phase, named for reference)

- **PolicyEvidenceAssembler** — deterministic, read-only assembly of
  cross-system evidence sets (§6.B) from existing canonical records.
- **LearningSignalDeriver** — deterministic derivation of learning
  signals (§7) from assembled evidence. Read-only.
- **PolicyGovernanceService** — the single mutation authority for the
  *governance lifecycle* (§8) only. It never writes effective policy
  directly: an accepted adaptation of an existing dimension is applied by
  calling the existing `CognitivePolicyEngine` path, so the engine's own
  validation, events, and reversibility apply. Analogous in role and
  discipline to `MaintenanceProposalService`.
- **PolicyRuntimeCoordinator** — turn-scoped inspection and evaluation,
  bounded exactly like `MaintenanceRuntimeCoordinator` (one top-level
  call per turn, correlation-scoped, no subscriptions, no recursion).

These are roles, not license for parallel infrastructure: they must be
composed in the existing composition root, hold references to the same
service instances, and keep no process-global state.

## 5. Policy domains

V10.2 supports exactly four domains. A proposal naming any other domain
is rejected deterministically at validation. Three of the four domains
target **existing** `CognitivePolicyEngine` dimensions; one (§5.4) is a
genuinely new domain that requires an explicit implementation decision.

### 5.1 ATTENTION POLICY (existing dimensions, new governance)

Evidence-backed adaptation of the existing behavioural dimensions
`interruption_tolerance` and `silence_tolerance`. The existing
`AttentionEngine` / `AttentionEngineV2` remain the actual attention
decision consumers — V10.2 does not create a second attention engine and
does not add a new attention input channel. What V10.2 adds: the ability
for cross-system evidence (e.g. N observed interventions in a scope that
were dismissed) to justify a *governed, confirmable* adaptation of those
dimensions, instead of relying only on V8.2 weak-signal accumulation.

### 5.2 DECISION POLICY (existing dimensions distinguished from new adaptation)

The existing dimensions `planning_preference` and
`recommendation_preference` are behavioural preferences about decision
*presentation* — they already exist and stay owned by the V8.2 engine.
V10.2 distinguishes two things that MUST NOT be conflated:

- **Adaptation of the existing presentation dimensions** from
  cross-system evidence (governed like §5.1).
- **New evidence-backed decision-guidance influence** — admitting a
  bounded, evidence-linked context item into decision guidance when a
  demonstrated pattern has observed outcomes. This second capability has
  no existing policy dimension; whether it is expressed as an additive
  vocabulary extension or a governance-only construct is an explicit
  CORE-phase decision (§22). It never decides for the user and never
  suppresses alternatives silently.

### 5.3 AUTONOMY POLICY (behavioural preference ≠ action authority)

This boundary is critical and must never blur:

- **`CognitivePolicyEngine.autonomy_preference` = user behavioural
  preference** (ask_first / act_low_risk / act). It expresses how much
  the user *wants* done without confirmation. It exists today.
- **`AutonomyGovernor` = actual action authorization authority.** Its
  rules, thresholds, and five dispositions (ACT / ASK / WAIT /
  DO_NOTHING / BLOCKED) decide what actually happens. It exists today
  and is unchanged by V10.2.

V10.2 may govern evidence-backed adaptation of the *former* (e.g.
repeated observed clean outcomes in a low-risk class justify proposing
`autonomy_preference: ask_first → act_low_risk`, with confirmation).
V10.2 MUST NOT replace, weaken, or bypass the *latter*: the final action
disposition still comes from the existing AutonomyGovernor, whatever the
preference says. **Irreversible actions remain ASK/BLOCKED exactly as
existing governor rules require; no adaptation may relax that, ever** —
an adaptation attempting to touch irreversible-action handling is invalid
at validation, not merely blocked at apply time. Any adaptation that
would make behavior *less* conservative requires explicit confirmation
(§9) with the evidence shown.

### 5.4 MODEL HANDLING POLICY (NEW V10.2 domain — explicit decision required)

**There is currently no generic model-handling policy engine, and no
existing `CognitivePolicyEngine` dimension covers this.** V10.2 must not
silently assume such support exists. This is a genuinely new domain
requiring an explicit implementation decision at CORE phase (§22):
whether it becomes additive dimensions in the existing engine, or a
governance-only construct consumed at the capability-execution seam.

Its intent, once decided: repeated evidence-backed model-error patterns
(via the existing ModelErrorService) may justify bounded changes to
model-assisted execution among strategies the system already has —
requesting additional verification for an output class, preferring the
deterministic path where one exists (CapabilityRouter truthfulness
unchanged), or degrading more conservatively on a specific model path. A
model-handling adaptation can never enable an honestly-unavailable
capability and never silences honest degradation reporting.

In all domains: no arbitrary natural-language rules. Targets come from
finite, enumerated, testable vocabularies — for existing dimensions, the
vocabulary is exactly the `CognitivePolicyEngine` value set already in
the code; for new constructs, the vocabulary is fixed at CORE phase.
Free text appears only in human-facing explanation fields.

## 6. Evidence model

V10.2 **builds on** the existing V8.2 policy evidence model; it does not
replace it, and it never bypasses the V8.2 validation rules
(`STRONG`-applies-immediately, `WEAK × WEAK_EVIDENCE_REQUIRED`,
`MIN_CONFIDENCE_TO_APPLY`). Two evidence classes are explicitly
distinguished:

### 6.A Existing V8.2 direct behavioural preference evidence (implemented today)

- **Explicit utterance** — the user says it outright
  (`apply_utterance()` / `observe()` at `STRONG = 0.9`); applied
  immediately by the existing engine; RECORDED authority.
- **Repeated weak behavioural signals** — inferred from behaviour at
  `WEAK = 0.25`; the existing engine changes nothing until
  `WEAK_EVIDENCE_REQUIRED = 3` consistent signals accumulate.

This class remains owned end-to-end by the existing engine. V10.2 reads
it (for conflict detection and context) but never intercepts or
re-implements it.

### 6.B New V10.2 cross-system learning evidence

Canonical records that the V8.2 evidence vocabulary does not consume
today:

- evaluated predictions (`predictions` rows with `evaluated_at`, via the
  PredictionEngine — an unevaluated prediction is not evidence);
- model-error records (ModelErrorService classifications);
- decision outcomes (decision records with observed outcomes);
- intervention outcomes (interventions and recorded suppressions,
  including user reactions where canonically captured);
- autonomy dispositions with observed consequences (trace/events);
- existing Skill/Principle evidence from canonical learning (referenced,
  never copied — §13);
- other canonical outcome records, and contradiction-resolution history
  where relevant to the target behavior.

**V10.2 may use class B to decide whether adaptation of an existing
policy dimension is justified.** When an adaptation is accepted, it is
applied through the existing engine's own path so that the V8.2
validation rules still hold; cross-system evidence justifies *proposing*,
never *forcing*, a change.

Inadmissible as evidence: raw model output; unevaluated predictions;
**any policy's existence or current state** (§10.6); paraphrases of
evidence; anything outside the verified user+tenant scope.

### 6.1 Minimum evidence requirements

- **A single anecdote MUST NOT automatically become an adaptation.**
- A class-B candidate requires at least **N independent supporting
  episodes** (N ≥ 3 as the specification default — deliberately no
  weaker than the existing `WEAK_EVIDENCE_REQUIRED = 3`; per-domain
  values fixed at CORE phase), where “independent” means distinct
  correlation IDs from distinct turns.
- Episodes must span at least two distinct sessions/days for the
  ATTENTION/DECISION/AUTONOMY domains (temporal spread guard). An
  explicit user instruction (§9.3) is class-A STRONG authority, not
  inference, and follows the existing engine's immediate-apply rule.

### 6.2 Evidence quality, scope, and provenance

Each evidence item carries: canonical record reference (kind + id),
correlation ID, timestamp, epistemic state (OBSERVED or RECORDED at the
leaf), and provenance (which service produced it). INFERRED aggregates
carry their derivation rule and inputs. Evidence outside the candidate's
declared scope does not count toward its minimums.

### 6.3 Temporal validity and staleness

Class-B evidence has a freshness horizon per domain (fixed at CORE
phase). Stale evidence still exists (never deleted) but stops counting
toward sufficiency; an adaptation whose supporting evidence has entirely
gone stale becomes EXPIRED-eligible (§8, §12). Every candidate records
the evidence window it was computed from.

### 6.4 Conflicting and insufficient evidence

Conflicting evidence (episodes supporting the opposite tendency, or
fresh class-A signals disagreeing with class-B inference) is counted,
referenced, and reported alongside supporting evidence; a candidate with
conflict ratio above the domain threshold cannot leave VALIDATING and is
reported with both sides. Insufficient evidence is an explicit,
user-visible outcome (“INSUFFICIENT EVIDENCE — n of N episodes, window
W”), mirroring `PredictionEngine.observe()` and the V10.1 BLOCKED
discipline. It never silently converts into a weaker claim.

### 6.5 Confidence boundaries

Governance confidence is derived deterministically from evidence count,
spread, conflict ratio and freshness — never from model self-assessment —
and is separate from the existing engine's per-dimension confidence
column, which the engine continues to own. Where an accepted adaptation
is applied through the engine, the engine's own confidence rules
(`MIN_CONFIDENCE_TO_APPLY`) still govern whether the value takes effect.

## 7. Learning signal

A **learning signal** is a deterministic, evidence-linked classification
stating that a repeatable pattern exists in canonical class-B records.
Initial catalog (extensible only by future spec revision):

| Signal | Derived from |
| --- | --- |
| REPEATED_FALSE_POSITIVE_INTERVENTION | N interventions in scope dismissed/negatively received |
| REPEATED_SUCCESSFUL_INTERVENTION | N interventions in scope accepted/acted on |
| REPEATED_PREDICTION_FAILURE_OF_CLASS | N evaluated-incorrect predictions of one class/scope |
| REPEATED_SUCCESSFUL_DECISION_PATTERN | N decisions matching a pattern with observed positive outcomes |
| REPEATED_AUTONOMY_SUCCESS | N ACT dispositions in a risk class with clean observed outcomes |
| REPEATED_AUTONOMY_FAILURE | N ACT/ASK dispositions in a risk class followed by observed problems |
| REPEATED_MODEL_ERROR_CLASS | N model errors of one classification on one path |

Rules: every signal instance lists the exact canonical records it was
derived from — a signal with unreferenced support is invalid; signals are
INFERRED statements (§3.4), inputs to candidacy, never adaptations, and
have no runtime influence themselves; derivation is pure counting/
matching over canonical records with fixed thresholds — no model call is
required or permitted to derive a signal. This deriver is not a second
learning engine: it consumes existing canonical records (including
LearningEngine outputs by reference) and produces only governance inputs.

## 8. Governance lifecycle

### 8.1 What exists today vs what is new

**Implemented today (V8.2 current-policy state):** per-dimension current
value with default/learned status, confidence, evidence rows,
`policy.proposed` when a weak signal is noted but below threshold,
`policy.updated` when a value actually changes, `policy.reverted` on
revert. This is the *current-policy* state machine and it stays exactly
as it is.

**New V10.2 concepts (NOT implemented; this specification defines
them):** every state below — CANDIDATE, VALIDATING, PROPOSED (as a
governed lifecycle state with a decision boundary, distinct from the
existing `policy.proposed` below-threshold event), ACCEPTED, ACTIVE (as
“applied and eligible for measured influence”), WEAKENED, DEFERRED,
SUPERSEDED, EXPIRED, REJECTED — plus measurement plans and effectiveness
observations. The V10.2 lifecycle is a **future governance lifecycle
layered above** the V8.2 current-policy state; it never replaces or
mirrors the engine's own state, and this specification does not pretend
any of it exists yet.

### 8.2 Lifecycle and transition authority

```
CANDIDATE → VALIDATING → PROPOSED → ACCEPTED → ACTIVE
                                        ACTIVE → WEAKENED / DEFERRED
                                        ACTIVE → SUPERSEDED / EXPIRED
              any pre-ACTIVE state → REJECTED
```

| Transition | Who/what may perform it |
| --- | --- |
| (create) → CANDIDATE | PolicyRuntimeCoordinator, from a learning signal meeting §6 minimums; or user explicit instruction (§9.3). |
| CANDIDATE → VALIDATING | PolicyGovernanceService, deterministically (evidence re-check, scope validation, conflict scan incl. fresh class-A signals). Automatic; no model involvement. |
| VALIDATING → PROPOSED | PolicyGovernanceService, only if all §6 gates pass. Otherwise the candidate is parked with an explicit insufficient/conflicting verdict. |
| PROPOSED → ACCEPTED | Explicit user confirmation through the existing confirmation boundary, governed by the AutonomyGovernor — except the narrow case in §9.2. |
| PROPOSED → REJECTED | Explicit user rejection; or deterministic invalidation (evidence withdrawn, scope invalid). Rejection is recorded as evidence. |
| ACCEPTED → ACTIVE | PolicyGovernanceService: registers the measurement plan, then applies the change **through the existing engine path** for existing dimensions (the engine emits its own `policy.updated`); for §5.4-type constructs, through the seam decided at CORE phase. |
| ACTIVE → WEAKENED | PolicyGovernanceService on measured harmful/neutral outcomes (§12) or user instruction. |
| ACTIVE → DEFERRED | User instruction (“not now”); influence ends; evidence retained. |
| ACTIVE/WEAKENED → SUPERSEDED | PolicyGovernanceService when a newer confirmed adaptation replaces it. Never destructive. |
| ACTIVE/WEAKENED/DEFERRED → EXPIRED | PolicyGovernanceService when temporal validity or evidence freshness runs out (checked interaction-driven, §10 — no scheduler). |

Invariants: mutation authority is deterministic — only
PolicyGovernanceService writes governance-lifecycle state, and only along
these edges; **model output cannot directly mutate policy or governance
state**; every transition is a canonical event with correlation ID,
reason, and evidence references; governance history is append-only —
SUPERSEDED/EXPIRED/REJECTED records are retained and reconstructable;
and where deactivation must change current behavior, it flows through
the existing engine's `revert()`/update path, never around it.

## 9. Authority model

### 9.1 Chain (preserved exactly)

```
user intent → evidence → proposal → AutonomyGovernor → canonical mutation
```

For existing dimensions the terminal canonical mutation is the existing
`CognitivePolicyEngine` write path, with its events and reversibility.

### 9.2 Confirmation matrix

| Mutation | Explicit confirmation required? |
| --- | --- |
| Create CANDIDATE / run VALIDATING | No (read-derived, no behavioral effect). |
| PROPOSED → ACCEPTED for any cross-system-evidence adaptation that increases system initiative, intervention, autonomy preference, or model-path trust (incl. every `autonomy_preference` step toward `act`, every §5.4 trust increase) | **Yes, always.** |
| PROPOSED → ACCEPTED for a strictly more-conservative, fully reversible adaptation (only reduces initiative/intervention/trust) | Confirmation is the default; implementation MAY auto-accept only if the AutonomyGovernor disposition is ACT for that mutation class — and must still notify with evidence. This is the only auto-accept window (kept-or-removed decision in §22; default on ambiguity: remove). |
| Class-A explicit utterance (existing behavior) | Unchanged: the existing engine applies STRONG utterances immediately, as released. V10.2 does not add a confirmation step to existing V8.2 behavior and does not remove one. |
| WEAKEN / DEFER / REJECT an adaptation | User instruction always honored; system-initiated WEAKEN on measured harm is deterministic and notified. |
| SUPERSEDE | Same confirmation class as accepting the replacing adaptation. |
| Anything touching irreversible-action handling | Impossible by construction (§5.3), not merely confirmed. |

### 9.3 Explicit user instruction

A direct, unambiguous user instruction (“always ask me before X”, “stop
interrupting me about Y”) is RECORDED class-A authority handled by the
existing engine (`apply_utterance()` semantics). V10.2 additionally
registers a measurement plan for the resulting change where a governed
adaptation exists for that dimension, but adds no friction to the
existing immediate-apply behavior.

### 9.4 What the model may and may not do

The model MAY: identify evidence (retrieval/summarization over canonical
records), summarize evidence for presentation, suggest an adaptation
candidate in conversation.

The model MAY NOT: directly activate any adaptation or write any policy
value; increase any authority or preference by itself; remove or relax
safety boundaries; alter historical evidence; delete contradictions;
erase model errors; cause any lifecycle transition except by the user
explicitly acting on what they read.

## 10. Runtime integration

### 10.1 Turn shape (intended)

```
USER TURN
→ perception
→ meaning
→ personal/world context
→ ADAPTIVE-POLICY INSPECTION            (new, read-only; §10.2)
→ existing cognitive execution           (existing consumers read
                                          CognitivePolicyEngine.effective()
                                          exactly as today)
→ outcome observation
→ consequence / model-error analysis     (existing)
→ ADAPTIVE-POLICY EVALUATION             (new, bounded; §10.3)
→ candidate proposal if justified
→ confirmation if required               (existing boundary)
→ canonical update                       (through the existing engine path)
→ future turn consumes the adapted policy (§11)
```

### 10.2 Where inspection happens (exactly)

Current effective policy already reaches existing consumers through
`CognitivePolicyEngine.effective()` — V10.2 does not reroute that.
V10.2 inspection is a single read-only governance call inside
`Cognition.process_turn`, after personal/world context assembly and
before capability execution. It determines which ACTIVE governed
adaptations are relevant to this turn's scope and records a consultation
entry (adaptation id, matched scope, consumer) — written to
ExecutionTrace/EventBus only when a consumer actually operates under the
adapted value (§11.2). Inspection performs no mutation, no model call,
and no evidence assembly.

### 10.3 Where evaluation happens (exactly)

Policy-governance evaluation is a single bounded step in the same
post-execution window where the V10.1
`MaintenanceRuntimeCoordinator.run_for_turn` operates — after outcome
observation and model-error analysis, using only records that already
exist for this turn plus canonical history. It:

1. records effectiveness observations for ACTIVE adaptations consulted
   in a *previous* turn that now have a measurable outcome (§12);
2. derives learning signals if this turn's canonical records complete a
   §6 threshold (deterministic relevance pre-gate, mirroring the V10.1
   relevance gate: no full evaluation on ordinary turns);
3. creates/advances at most a bounded number of candidates (cap fixed at
   CORE phase) and surfaces any resulting PROPOSED adaptations in the
   turn context exactly like V10.1 surfaces maintenance proposals
   (merged, deduplicated, correlation-scoped — the PR #14 visibility
   rule: nothing may be created without being surfaced).

### 10.4 Interaction with V10.1 maintenance (no recursion)

Policy-governance evaluation and maintenance are sibling bounded steps
under the same turn correlation; neither subscribes to the other's
events. A maintenance re-audit correlation (`::reaudit1`) never triggers
governance evaluation; a governance-evaluation correlation marker
(terminal suffix, analogous to `::reaudit1`, fixed at CORE phase) never
triggers maintenance, re-audit, or further governance evaluation. Depth
bounds are provable from persisted correlation IDs, as in V10.1. A
confirmed adaptation may trigger at most **one** bounded re-evaluation of
its domain (mirror of the V10.1 depth-1 re-audit), idempotent by
correlation uniqueness.

### 10.5 Hard bounds

Maximum **one** top-level adaptive-policy evaluation per conversational
turn (idempotent per correlation). No policy-triggered recursive policy
loop. Bounded re-evaluation only (depth 1). No scheduler, no polling
loop, no background task, no event-subscriber recursion. Expiry checks
run interaction-driven, inside the bounded evaluation step only.

### 10.6 Recursion / self-reference (binding rules)

- **Policies are not evidence for policies.** Neither the existing
  engine's rows nor governance records are admissible class-B evidence.
- **An adaptation's current state cannot independently validate
  itself.** Validation consults only external canonical evidence.
- **The adaptation being evaluated cannot count as evidence for its own
  promotion** — including indirectly (e.g. its consultation events are
  measurement inputs (§12), never adaptation evidence (§6)).
- **Recursive policy → policy → policy adaptation is forbidden.** No
  chain of adaptations may justify another adaptation at any depth.
- **Existing policy state may be a context input** (scope matching,
  conflict detection, knowing the current value being adapted) **but is
  never self-validating evidence.**

## 11. Future-turn influence (the core requirement)

An ACCEPTED/ACTIVE adaptation MUST actually affect a later turn through
an existing canonical consumer. Influence that cannot be observed in
ExecutionTrace/EventBus does not count as influence.

### 11.1 Per-domain influence paths (existing components only)

| Domain | Path | Effect shape |
| --- | --- | --- |
| ATTENTION | Adapted `interruption_tolerance` / `silence_tolerance` via the existing engine → existing `AttentionEngine`/`AttentionEngineV2` consumption | The attention decision operates under the adapted value; the disposition/suppression record cites the governed adaptation id among its reasons. |
| DECISION | Adapted `planning_preference` / `recommendation_preference` via the existing engine; plus (if ratified at CORE phase) the bounded decision-guidance context item | Presentation follows the adapted value; any guidance item is trace-attributed to adaptation id P. |
| AUTONOMY | Adapted `autonomy_preference` via the existing engine → wherever the released pipeline already consumes that preference | The behavioural preference changes; **the AutonomyGovernor's disposition logic is untouched and still decides**; the disposition payload records the preference input and its source adaptation. Never a bypass. |
| MODEL HANDLING | The §5.4 seam decided at CORE phase | Verification/degradation strategy selection among existing strategies; ExecutionTrace records strategy and source adaptation. |

### 11.2 Truthfulness rule

**No “policy applied” event may exist without actual behavioral
influence.** The consultation event is emitted at the point where a
consumer actually operates under the adapted value — not when the
governance layer hands anything over. If no consumer used it, no
influence event exists, and measurement records non-consultation rather
than pretending effect.

### 11.3 Observability

For every influenced turn: ExecutionTrace contains the consumer, the
adaptation id, the matched scope, and what concretely differed; the
EventBus carries an additive V10.2 consultation event (final vocabulary
at CORE phase, §4.4) under the turn correlation. This is the evidence
base for §12.

## 12. Measurement

### 12.1 Two evidence roles, never confused

- **ADAPTATION EVIDENCE** — why the adaptation was proposed/accepted
  (§6). Frozen at acceptance; never retroactively edited.
- **OUTCOME EVIDENCE** — whether the changed policy actually worked:
  canonical outcomes of turns influenced under §11. Accumulated after
  activation.

Outcome evidence must NOT be counted as adaptation evidence for the same
or any other adaptation (§10.6); adaptation evidence must not be
re-counted as effectiveness. The two sets are stored and reported with
distinct roles.

### 12.2 Loop

```
declared expected effect (at proposal time)
→ later outcomes of influenced turns (canonical records)
→ deterministic comparison of expectation vs reality
→ effectiveness observation (stored, evidence-linked)
→ retain / weaken / supersede / expire
```

### 12.3 Effectiveness observation categories

Per influenced turn (or declared measurement unit): SUCCESSFUL_INFLUENCE
(declared expected effect observed), NEUTRAL_INFLUENCE (behavior
differed; outcome neither matched nor contradicted expectation),
HARMFUL_INFLUENCE (outcome contradicted the expected effect),
INSUFFICIENT_EVIDENCE (outcome not observable for this unit; stated
explicitly, counted as coverage gap, never guessed),
CONFLICTING_OUTCOMES (mixed results within the unit; reported with both
sides, resolved only by more evidence).

### 12.4 Rules

- The system MUST NOT claim effectiveness without evidence: an
  adaptation with zero effectiveness observations reports “no measured
  outcomes yet”, not success.
- **Sample sizes**: retain/weaken/supersede decisions require the
  domain's minimum observation count (fixed at CORE phase; ≥ 3 as the
  specification default). Below the minimum the adaptation stays ACTIVE
  with an explicit under-measured status — unless HARMFUL observations
  occur, which may trigger deterministic WEAKEN at a lower threshold
  (safety asymmetry).
- **Stale adaptation**: no matching influenced turns within the
  freshness horizon → flagged stale, EXPIRED-eligible, executed
  interaction-driven (§10.5).
- **No aggregate “policy score”.** Effectiveness is reported per
  category with counts, windows, and evidence references — never one
  number.

## 13. Conflict handling

| Situation | Required behavior |
| --- | --- |
| New class-B evidence contradicts an ACTIVE adaptation | Record it; past the §6 conflict threshold, deterministically WEAKEN and surface a re-validation proposal. Never silently keep full influence. |
| Adaptation conflicts with a newer explicit preference (class-A STRONG) | The existing engine has already applied the user's utterance (released behavior). Governance immediately marks the adaptation WEAKENED/SUPERSEDED-candidate — RECORDED authority outranks INFERRED adaptation, and V10.2 never fights the engine for the current value. |
| Adaptation becomes stale | §12.4 stale flow. |
| Scope changes (entity/topic no longer exists or split) | Adaptation flagged scope-invalid, loses influence eligibility, rescope proposal surfaced; original retained. |
| Context changes (capability/model path removed) | §5.4 adaptations on that path become dormant (explicit status), not deleted. |
| Model performance changes (error class stops recurring) | Measurement records it; normal weaken/expire flow. No auto-strengthening without confirmed re-proposal. |
| User explicitly rejects the adaptation | REJECTED immediately; if it had been applied, the current value is restored through the existing engine's revert/update path; rejection stored as evidence against similar future candidates. |
| Two candidates conflict | Neither reaches PROPOSED silently; both surfaced together with their evidence; at most one can be accepted, the other REJECTED with cross-reference. |

V10.2 governance history is append-only and must retain its own
governance and evidence records; V10.2 introduces no destructive
deletion path for governance records, and prefers supersession/
versioning always. This guarantee is scoped to V10.2's own records: it
is NOT a claim that legacy `policies` rows are historically preserved —
both released legacy revert paths delete the current `policies` row
(§3.1), and that behavior remains unchanged in V10.2. How a
governance-history reference relates to a legacy `policies` row that was
later deleted through either legacy path is explicitly deferred to Open
Question #9 (§22).

**LearningEngine / Skills / Principles boundary:** the existing
`LearningEngine` is the canonical learning/evidence source (Experience →
Skill → Principle, plus its released policy pattern mining over the same
`policies` table). V10.2 does not duplicate any of it: it does not mine
patterns the LearningEngine already mines, does not create Skills or
Principles, and does not create another learning engine. V10.2
governance decides **when cross-system learning evidence may justify
changing existing behavioural policy** — a decision layer the
LearningEngine does not provide. Skill/Principle ≠ policy: Skills and
Principles state what was learned; behavioural policy states how the
system behaves. An adaptation may cite Skills/Principles as evidence
**by reference** (kind + id + version), never copying, re-storing,
re-scoring, or superseding them. Retiring a cited Skill/Principle
triggers the conflicting-evidence flow above.

## 14. Security / tenancy

V8.5 is reused exactly. All governance reads and writes flow through:

```
verified Principal → verified user → verified tenant → canonical service lookup
```

- No caller-provided `user_id` may override verified identity — the
  existing substitution rule applies to every V10.2 read, proposal,
  confirmation, measurement, and export path.
- **Direct-ID isolation:** requesting any adaptation, candidate, evidence
  set, effectiveness observation, or consultation record by direct ID
  from outside the verified user+tenant scope returns the same not-found
  behavior as existing V10 services (no existence oracle).
- Evidence assembly is scope-bound at the query level (the
  `_canonical_scope` discipline), not filtered after the fact.
- The existing `policies` table remains user-scoped exactly as released;
  V10.2 adds no new access path to it that weakens scoping.
- Cross-thread reads within one verified user remain permitted exactly
  as today; adaptations are user-scoped unless their declared scope
  narrows them.

## 15. Portability

V10.2 reuses the existing `memory-os-export` architecture. No second
format. The `policies` table already participates in the released
portability system; V10.2 adds governance records additively.

- **Export representation:** governance adaptations, lifecycle history,
  evidence references (as references — the referenced canonical records
  including `policies` rows are already exported), learning-signal
  derivations, effectiveness observations, and consultation records,
  under an additive section version marker (following the
  `maintenance_schema_version` precedent).
- **Provenance preservation:** epistemic states, derivation rules, and
  evidence references survive export/restore byte-faithfully.
- **Lifecycle preservation:** full transition history exported; restore
  reproduces state and history, not just the latest state.
- **Scope preservation:** user/tenant scope validated on restore through
  existing identity checks; nothing restores into a different verified
  scope.
- **Restore validation:** referenced evidence must exist in the same
  package or already in the target store; dangling references fail
  validation with explicit reasons (existing validation discipline).
- **Duplicate/conflict handling:** re-import of an existing governance
  record id is idempotent; same-id different-content import is rejected
  with both fingerprints reported, mirroring existing conflict rules.
  Restore never overwrites the live `policies` current values outside
  the existing portability semantics for that table.

## 17. Cognitive Health

V10.2 contributes evidence-backed dimensions to the existing Cognitive

single overall number.**

| --- | --- |

## 18. API boundary (responsibilities only — no implementation)

Intended responsibilities, separated; every mutation is
authorization-aware through the V8.5 boundary and the §9 matrix. The
existing policy read surface (the engine's `list()` / `explain()` data)
remains what it is; V10.2 responsibilities are additive governance views:

| Responsibility | Nature | Notes |
| --- | --- | --- |
| READ | Read-only | List/get adaptations, lifecycle history, evidence sets, effectiveness observations; scope-filtered; UNKNOWN and insufficient states are first-class response values. |
| PROPOSE | Mutation (create PROPOSED via full §6/§8 gate) | Internal derivation is primary; a user-initiated path exists for §9.3 instructions (which the existing engine applies; governance registers measurement). |
| CONFIRM | Mutation | Explicit acceptance; governor-gated; applies through the existing engine path; returns the applied result and any bounded re-evaluation outcome (additive, like the V10.1 confirm → `reaudit` pattern). |
| REJECT | Mutation | Explicit rejection with reason; recorded as evidence. |
| DEFER | Mutation | Explicit deferral; no influence while deferred. |
| INSPECT | Read-only | Explain a specific adaptation: evidence, derivation, consultations, measurements — alongside (not replacing) the engine's own `explain()`. |
| MEASURE | Read-only trigger boundary | Expose measurement state; any recomputation stays inside the bounded turn step — never a scheduler substitute. |

Prefer internal service integration over new endpoints where existing
endpoints can carry additive fields (established V10.1 precedent).
Endpoint decisions are CORE/RUNTIME-phase work.
