# MEMORY//OS V8.4.4 — Data Portability, Export and Recovery

V8.4.4 adds a real user-owned portability and recovery subsystem. It extends
the existing SQLite persistence layer, cognitive EventBus, ExplanationEngine,
API conventions, and conversational tool registry. It does not create a second
database, memory store, event bus, or recovery engine.

## Architecture

```text
existing SQLite cognitive tables
          │
          ├── PortabilityService
          │     ├── deterministic JSON table snapshots
          │     ├── manifest + per-file/object SHA-256 hashes
          │     ├── bounded ZIP package + human report
          │     └── validation / conflict / restore transaction
          │
existing EventBus ◄── export/import/restore audit events
existing ExplanationEngine ◄── manifest, validation, conflict and restore explanations
```

`PortabilityService` is wired in `Runtime` and receives the existing `Database`
and `cognition.bus`. The additive `SCHEMA_V844` creates operational records for
exports, staged imports, validation results, plans, conflicts and operations.
Cognitive records remain in their original V8.3/V8.4 tables.

## Export format

An export is a ZIP package with a versioned `manifest.json`, `integrity.json`,
deterministically serialized `data/<table>.json` snapshots, `relationships.json`,
`metadata/configuration.json`, and `report.md`.

The manifest records:

- format and schema version (`memory-os-export`, format `1`, schema `8.4.4`);
- owner scope, export timestamp, selected domains and object counts;
- per-file SHA-256, byte count, record count and per-object hashes;
- ownership classification for user-generated data, derived state, external
evidence, configuration, and secrets;
- deterministic UTF-8 JSON serialization rules and explicit redactions.

The package contains the complete persisted cognitive surface available in the
existing database: memories and lifecycle/version history; events; world and
world history; intents, needs, experiences, skills, principles; causality,
predictions, decisions, missions/plans/goals/commitments; research and
provenance; explanations; conversations; and relevant non-secret metadata.

Secrets, API keys, tokens, passwords, session secrets, local paths, caches,
virtual environments, node modules and runtime databases are not exported.
Sensitive field names are redacted defensively before serialization.

## Restore lifecycle

```text
PACKAGE
 → MANIFEST VALIDATION
 → SCHEMA VALIDATION
 → INTEGRITY VALIDATION
 → STRUCTURAL / RELATIONSHIP VALIDATION
 → CONFLICT ANALYSIS
 → DRY RUN
 → EXPLICIT USER CONFIRMATION
 → TRANSACTIONAL APPLY
 → EVENTBUS AUDIT
 → VERIFY / HISTORY
```

Uploading a package only stages an untrusted ZIP. Validation parses JSON only;
no imported content is executed. A failed validation never touches cognitive
state. Applying a restore uses one SQLite `BEGIN IMMEDIATE` transaction and
rolls back on any insert or constraint failure. Re-running a restore is safe:
identical rows are reported as duplicates and are skipped.

Selective domains expand to safe provenance/audit dependencies. For example,
memories bring their versions, relationships, lifecycle data and required audit
records; skills/principles bring their evidence, validations, usages and
transitions. Dangling relationships are rejected rather than fabricated.

## Conflict semantics

Conflicts are persisted in `portability_conflicts` and returned explicitly.
States include `duplicate`, `local_newer`, `imported_newer`, and `divergent`.
Same identity with different lifecycle, provenance, relationship or contents is
never silently merged. Every non-duplicate conflict requires one explicit
choice: `skip`/`keep_local` or `replace`. `replace` is the only operation that
can update an existing record, and only when named by its conflict id.

The dry-run reports selected domains, dependencies, inserts, explicit updates,
skips, blockers and all conflicts. Confirmation is rejected if any selected
conflict remains unresolved.

## Security and resource limits

Imports are treated as hostile input. The validator rejects absolute paths,
`..` traversal, backslashes, duplicate filenames, symlinks, malformed UTF-8/
JSON, unknown tables/columns, unsupported schema versions, dangling references,
excessive nesting, object-count abuse, oversized members, oversized total
uncompressed data, suspicious ZIP compression ratios, and processing that
exceeds the configured deadline. ZIP members are never extracted to arbitrary
paths. Pickle and arbitrary-code deserialization are not used.

Instruction-like text in imported evidence is surfaced as an inert-data warning;
it is never executed or promoted into system instructions. The package integrity
model detects changed data or manifest contents against the recorded manifest
and integrity hashes. Package authenticity/signing is outside this local-first
release's scope and is documented as a limitation.

## APIs and tools

The distinct namespace is `/api/portability/v1/`:

- `POST /exports`, `GET /exports`, `GET /exports/{id}`,
`GET /exports/{id}/manifest`, `POST /exports/{id}/verify`, and download;
- multipart `POST /imports`, `GET /imports`, `GET /imports/{id}`;
- `POST /imports/{id}/validate`, `POST /imports/{id}/dry-run`,
`GET /imports/{id}/conflicts`;
- `POST /imports/{id}/restore-selected` (alias `/restore`), and
`GET /restore-history`;
- `GET /imports/{id}/explanation`.

Conversational adapters use the existing structured tool system:
`start_export`, `inspect_export`, `validate_import`, `dry_run_restore`,
`inspect_restore_conflicts`, `restore_selected`, and
`inspect_restore_history`.

The canonical EventBus emits `export.started`, `export.completed`,
`export.failed`, `import.started`, `import.validated`, `import.rejected`,
`restore.dry_run`, `restore.confirmed`, `restore.applied`, `restore.failed`,
`restore.rolled_back`, and `restore.conflict_detected`.

## Limitations

- Authentication remains the V8.4.3 local single-user model; the existing
`user_id` namespace is enforced, but this release does not add login/session
infrastructure.
- Packages use hash-based integrity metadata, not a cryptographic signature or
keyed authenticity service.
- The existing separate LangGraph checkpoint database is not exported as a
portable cognitive table; conversation messages and the persisted cognitive
records are exported. Checkpoint implementation details remain local runtime
state.
- Existing vector indexes are rebuildable derived state and are not included;
the authoritative memory rows, relationships and lifecycle history are.
- No implicit deletion exists. Removed records are not inferred from absence in
an export.
