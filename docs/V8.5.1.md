# V8.5.1 — Real-model cognitive tool routing reliability

Surgical correction on top of V8.5. No product redesign, no new architecture,
no change to the V8.5 security surface.

## The problem

Windows verification against a real local `llama3.2:3b` (Ollama) exposed five
reproducible failures in the real-model regression suites:

| # | Test | Input | Observed |
|---|------|-------|----------|
| 1 | `test_model_uses_mission_tools_for_a_natural_question` | "What missions am I currently working on?" | model chose `get_attention_state` instead of a mission-reading tool |
| 2 | `test_model_selects_resume_mission_for_resume_it` | "Resume it." (paused mission in focus) | no `resume_mission` TOOL_DECISION |
| 3 | `test_model_lists_missions_without_a_tool_failure` | "What missions am I currently working on?" | only `get_attention_state`; wrong subsystem |
| 4 | `test_real_model_selects_learned_inspection_tool` | "What skills have you learned, and what evidence supports them?" | no learned-inspection tool decision |
| 5 | `test_real_model_selects_explanation_tool_for_why` | "Why did you use that skill? What is it based on?" | no explain tool decision |

The provider was real. The tools worked. The model simply could not reliably
pick the right cognitive subsystem out of **~40 tool schemas** advertised at
once — a 3B model's tool-selection accuracy degrades sharply as the bound
tool count grows.

A second round of Windows verification, WITH the routing correction in
place, proved the narrowing works (trace: `TOOL_SURFACE families=['memory',
'missions']` → `TOOL_DECISION list_missions`) and exposed one residual
failure at the argument boundary: the model emitted
`{"open_only": "null"}` — the JSON null token serialised as a STRING —
which strict Pydantic validation rejected as `TOOL_FAILED`.

## Root cause

`MemoryAgent.agent_node` bound **every** tool (5 memory + ~35 cognitive) on
every turn via `model.bind_tools(tools)`. The existing `CapabilityRouter`
(V8.2) was wired onto the agent (`self.router`) but was **never consulted on
the model path** — it only fed `/api/provider` reporting and orchestrator
task routing. Nothing narrowed what the model had to choose between.

## The correction

The intended architecture is now real:

```
USER INPUT
  → CapabilityRouter.tool_surface(message, focus_kinds)   [existing router, new method]
  → relevant capability FAMILIES (missions / learned / explanation / …)
  → smaller advertised tool surface (bind_tools)
  → REAL MODEL chooses the final tool                     [genuine TOOL_DECISION]
  → tool executes (full registry — narrowing never blocks)
  → TOOL_RESULT recorded → model revision → response
```

- **Families, never tools.** `tool_surface()` activates whole capability
  families (8 of them, covering all 40 tools) from conservative word-boundary
  signals in the message plus live conversational focus kinds. A narrowed
  surface always contains every tool of every activated family, so the model
  keeps a genuine choice (e.g. "Resume it." advertises `pause_mission` AND
  `resume_mission` — the model still decides).
- **Cross-cutting tools survive.** The memory family is always offered
  (the system prompt requires `search_memory` before user questions).
- **Fail open.** No signal, a broad message (> 4 substantive families), no
  router, or any router error ⇒ the full surface is bound, unchanged from
  V8.5 behaviour.
- **Advertising only, never authorization.** `tools_node` still executes
  from the complete tool registry; an out-of-surface call by the model
  executes genuinely. (Authorization stays where V8.5 put it: server-side,
  per-user.)
- **Honest tracing.** The narrowing itself is recorded once per turn as a
  new `TOOL_SURFACE` trace stage (persisted in `execution_traces`, mirrored
  to the EventBus as `routing.tool_surface`, and visible in the chat
  activity trail). TOOL_DECISION entries still come exclusively from the
  model's own `tool_calls` — nothing is fabricated.
- **Sharper descriptions.** `get_attention_state` (the tool that stole
  mission questions) now states explicitly what it is NOT for;
  `list_learned` now names itself as the first tool for "what skills have
  you learned" questions, including when evidence is asked about.
- **Stringified-null argument normalisation AT THE EXECUTION BOUNDARY.**
  A third Windows trace proved schema-level tolerance alone was not
  sufficient on the real LangChain invocation path: routing was correct,
  `TOOL_DECISION list_missions` was correct, and the raw model dict
  `{"open_only": "null"}` still reached strict validation and failed. The
  normalisation therefore lives at the actual boundary between the model's
  raw `tool_calls` arguments and `tool.invoke`:
  `normalize_model_tool_args()` in `agent/execution.py`, called by
  `run_tool_safely` (the traced path used by `tools_node`) and by
  `_invoke_untraced` (standalone agents). It converts ONLY the exact
  lowercase string `"null"` — the one spelling JSON permits for its null
  token — to `None`, recursively through dicts/lists. Nothing else is
  coerced: `"true"`/`"false"` stay strings, and `"banana"`, `"None"`,
  `"NULL"`, `"nil"`, `""` still fail strict Pydantic validation as
  TOOL_FAILED with a real ValidationError. The `_NullTolerant` schema
  keeps its own defence in depth (real null → field default, plus the
  same token normalisation) for direct tool invocations that bypass the
  agent loop. Duplicate detection runs on the normalised arguments, so
  `{"open_only": "null"}` and `{"open_only": None}` are recognised as the
  same call.
- **Graph-handoff normalisation (legacy trace contract).** Windows
  verification with all five real-model tests green surfaced one last
  compatibility break: the V8.4.1 correction regression wraps
  `graph_module.run_tool_safely` and captures arguments BEFORE the
  boundary's internal normalisation, so it observed `item_id="null"`
  where the historical contract expects `None`/empty. `tools_node` now
  applies the SAME `normalize_model_tool_args` helper at the handoff —
  before calling `run_tool_safely` — so every downstream consumer
  (execution, historical wrappers, the persisted trace) sees one
  canonical argument representation. The boundary keeps its own
  idempotent normalisation as defence for other callers; there is one
  implementation, applied at two levels.

### Why this is not keyword routing

The forbidden pattern is *deciding the tool* from keywords. Here the final
tool choice is still made by the model, from a genuinely bound tool surface,
and appears in the trace only when the model emitted the call. The router
narrows which capability families are *presented* — the same role the
context builder already plays for facts (V8.3.1.2 put the focused mission in
the prompt; V8.5.1 puts the relevant families in the binding). The
deterministic fallback planner is unchanged and remains the only place with
message-conditional tool invocation, clearly labelled DETERMINISTIC.

## Testing

`backend/tests/test_v851_tool_routing.py` (40 tests, deterministic, seconds
not minutes):

- family selection for each of the five real-model failure messages;
- memory always offered; fail-open on no signal / broad message / router
  error / missing router;
- graph binds the narrowed surface; both model calls of a turn see one
  consistent surface; TOOL_SURFACE traced in activity + `execution_traces` +
  EventBus;
- out-of-surface model calls still execute (narrowing never blocks);
- demo/no-provider fallback contract unchanged;
- no fabricated TOOL_DECISION when the model answers without tools;
- static check that the real model path gained no command dispatch;
- stringified-null arguments THROUGH THE ACTUAL EXECUTION PATH
  (`run_tool_safely`, exactly as `tools_node` calls it — not
  `model_validate`): `{"open_only": "null"}` produces a clean TOOL_RESULT
  identical to a real null and to omitting the argument; real booleans
  preserved; `"true"`/`"false"` strings not coerced; invalid strings
  (`"banana"`, `"None"`, `"NULL"`, `"Null"`, `"nil"`, `""`) still fail as
  TOOL_FAILED with a real ValidationError; the untraced standalone path is
  covered; duplicate detection treats `"null"` and `None` as one call; and
  end-to-end through the graph a model call carrying `"null"` produces
  TOOL_RESULT with no TOOL_FAILED.

The five real-model tests themselves are unweakened and unmodified; they
require a live Ollama `llama3.2:3b` and skip loudly when it is absent.
