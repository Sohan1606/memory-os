# V8.4.1 Security Review

Date: 2026-09-18

## Scope

This review covers the V8.4.1 Experience, Skill and Principle persistence,
services, APIs, conversational tools, event/causal integration and Observatory
surface. It also records whole-application static and dependency scans so new
work is not evaluated in isolation.

## Threat model

| Threat | Control | Verification |
|---|---|---|
| Cross-user object read | Every Experience/Knowledge lookup includes `user_id`; unknown and foreign ids both return 404 | API isolation test, Scenario H |
| Cross-user evidence attachment | Observation, Experience and Skill evidence is resolved in the caller's namespace before insertion | fabricated/cross-user evidence test |
| Cross-user correction or causal traversal | Correction queries and causal graph traversal are user scoped | core isolation test, Scenario H |
| Model invents trusted guidance | Model output cannot promote; deterministic validation and an explicit promotion operation are required | validation rejection tests; background promotion=0 |
| Frequency creates false expertise | Skill requires three successful validated Experiences and distinct origins; Principle requires two Skills/two patterns/four Experiences | Skill/Principle rejection tests |
| Stale/wrong-context guidance is used | Lifecycle, scope and current-world preconditions are eligibility gates before arbitration | Scenario F |
| Retrieval is mistaken for successful influence | Retrieval counters are separate; use/reputation changes only after recorded influence/outcome | usage and insufficient-evidence tests |
| Outcome is fabricated | Supported/contradicted verdict without evidence is downgraded to `INSUFFICIENT EVIDENCE` | dedicated outcome test |
| Unsafe unattended learning | Existing background budgets/cancellation apply; maintenance may validate but never promote | background integration test |
| Destructive “forget” erases audit | Forget/stop-use is soft retirement; evidence and transitions remain | Scenario G |
| Private reasoning disclosure | Explanation output is evidence, validation, use and causal summaries only | API/tool/browser assertions |
| SQL injection through V8.4.1 counters | Values use bound parameters; column changes use a closed map of static SQL statements | Bandit produced no V8.4.1 medium/high finding |
| Arbitrary reset deletion | Reset is restricted to the configured demo user; V8.4.1 cleanup uses static table statements and user-bound parameters | API restriction and reset integration test |

## Namespace boundary and authentication

`user_id` remains a namespace, not authenticated identity. This is an existing,
documented local-first limitation. V8.4.1 preserves namespace isolation but does
not claim production multi-tenant authentication or authorization. Deployments
must not expose this demo API to untrusted networks as an authenticated service.

## Static analysis

Command:

```bash
python -m bandit -q -r app -f json
```

Result:

- baseline `779a5bf`: **0 high, 3 medium, 14 low**;
- V8.4.1: **0 high, 3 medium, 14 low**;
- net new findings: **0**;
- `experience.py` / `knowledge.py`: no findings;
- V8.4.1 reputation/reset SQL: no medium/high findings.

The three unchanged medium findings are Bandit B608 heuristics in legacy
allow-listed SQL builders (`autonomy.py`, the existing memory reputation
counter, and `world.py`). Inputs are constrained by closed internal enumerations
and query values remain bound. The 14 low findings are existing assert or
best-effort teardown/trace exception patterns. No finding was suppressed with
`# nosec`.

## JavaScript dependency audit

Initial scan found one moderate and two high advisories through bundled PostCSS
and Sharp. The release updates:

- `sharp` from `0.33.5` to `0.35.4`;
- root `postcss` to `8.5.28`;
- an npm override makes Next use the patched root PostCSS.

Fresh `npm ci` resolves Next to its existing `15.5.25` and deduplicates the
patched packages. Both scans pass:

```text
npm audit            → found 0 vulnerabilities
npm audit --omit=dev → found 0 vulnerabilities
```

The Next major version was deliberately not changed as part of V8.4.1.

## Python dependency audit

`python-multipart` was updated from `0.0.20` to `0.0.32`, resolving six 2026
path-traversal/parser/denial-of-service advisories relevant to request parsing.

Raw `pip-audit -r requirements.txt` then reports four advisories against
`chromadb==1.5.9`:

- `PYSEC-2026-311`;
- `PYSEC-2026-3813`;
- `PYSEC-2026-3814`;
- `PYSEC-2026-3815`.

At review time 1.5.9 is the newest published Chroma package and the advisory
feed provides **no fixed version**. All four attack paths target Chroma's
network `/api/v2` server and its server authorization/provider configuration.
MEMORY//OS does not start or expose that server: it uses Chroma's embedded
`PersistentClient` from the backend process, and browser traffic reaches only
the explicit FastAPI routes. No user-controlled model repository or
`trust_remote_code` setting is accepted by a MEMORY//OS route.

Accordingly the release gate runs the audit with these four ids explicitly
ignored **only after recording them here**:

```text
pip-audit ... --ignore-vuln <the four ids above>
→ No known vulnerabilities found, 4 ignored
```

This is an accepted no-fix, non-reachable risk—not a claim that the dependency
contains no advisory. It becomes applicable immediately if a deployment starts
Chroma's HTTP server; such a deployment must add network isolation/authentication
or move to a fixed release when one exists.

## Secret and artifact policy

The release artifact check rejects runtime `.env` files (while retaining the
pre-existing credential-free `.env.example`), credentials, keys/tokens, SQLite
DB/WAL/SHM files, `.venv`, `node_modules`, `.next`, caches, debug dumps and
temporary files. Pattern scans cover private-key headers and common provider
credential assignments. Test strings mentioning API-key variable names are not
credentials.

## Residual risks

1. No application authentication; local/demo namespace only.
2. Accepted Chroma advisories have no upstream fixed version and are safe only
   while Chroma remains embedded and unexposed.
3. CORS defaults to `*`, suitable for local demo behavior, not an authenticated
   Internet service.
4. A real model can choose the wrong conversational tool. The model path remains
   constrained by server-side user binding, lifecycle/scope checks and
   evidence-gated promotion; real-model selection itself was not verifiable in
   this environment because Ollama was absent.
5. SQLite/Chroma are single-node local stores; filesystem access remains a trust
   boundary.

## Security gate decision

**PASS WITH DOCUMENTED ACCEPTED DEPENDENCY RISK.** There are no new static
findings, no npm advisories, and no fixable Python advisories after the
`python-multipart` update. Four Chroma server advisories are openly recorded,
have no fixed release, and are not reachable in the supported embedded
architecture.
